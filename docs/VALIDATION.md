## 1. 先说这次实验不能证明什么

**候选是我（同一个模型）生成的，意图也是我写的。** 生成器与出题人同源，
所以"首次通过率""收敛轮数"这两个数在这份报告里**只反映方法学能不能跑，不反映方法有多好**。
真正的结论需要作者从自己不可控的模型独立取候选复跑（NEXT P6 仍算未完成，见 §6）。

这条声明放在最前面，是因为它决定了下面所有数字的解释方式。

## 2. 三题（都在 D0 子集里）

| 任务 | 签名 | 人写的意图（除签名外仅此） | 形状 |
| --- | --- | --- | --- |
| A | `fn size_ok(n: u64) -> bool` | 3 条 `example`：`size_ok(0) == false`、`size_ok(8388608) == true`、`size_ok(8388609) == false` | 边界敏感 |
| B | `fn retryable(e: ApiError) -> bool` | 3 条 `example`：`IoError == true`、`PreconditionFailed == true`、`NotFound == false` | 分支密集 |
| C | `fn can_write(prev: u64, if_match: u64, body_len: u64) -> bool` | 3 条 `example`：`(0,5,10) == false`、`(5,5,10) == true`、`(5,4,10) == false` | 三参数决定 |

三个任务都刻意**不涉及循环、能力调用、模块** —— 也正是当前语言装得下的全部形状。
每题三个候选（`a.dlt` / `b.dlt` / `c.dlt`），各用一种自然写法：早守卫 / 合取 / 逐层嵌套 /
通配分支 / 全列举分支。候选在跑工具**之前冻结**，之后没有为了让它过而改过实现。

`intent.dlt` 里额外放了一个**占位实现**当靶子（看 §4 第 3 条）。

## 3. 结果一览

| 任务 | 首次通过 | 自动输入 | 第 1 轮存活 | 人补的 example | 最终存活 | 存活者可否观测地不同 | 变异 MISS 账 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A | 3/3 | 9 条 | 3 | 1 条 | 3 | **否**（三个候选等价） | 1 → 0（补的那条命中） |
| B | 3/3 | **0 条** | 3 | 3 条 | 2 | **否**（a 与 b 等价，c 已被否） | 14 → 12（剩的全是等价变异） |
| C | 3/3 | 25 条 | 3 | 2 条 | 3 | **否**（三个候选等价） | 4 → 0（第 1 条没命中，第 2 条命中） |

命令：`droplet verify <候选>`（样例 + 四类变异）、`droplet explore a.dlt b.dlt c.dlt`（样例对齐 + 生成输入）。
候选之间**没有产生一条分歧**（除了 B 里 `Conflict` 那条我特意让人补的样例点出来的），
自动输入也没抓到任何东西 —— 因为要比较的候选本来就没有行为差异。
**0/3 收敛到唯一存活**，三题都退出码 1（判据 A：工具不替人挑）。

## 4. 撞出来的六条事实（预写的三条判据都没覆盖它们）

1. **`explore` 的收敛判定比判据 A 更严，而且严在了一个不可能满足的地方。**
   SPEC §7.8.3-1 写的是：存活候选之间存在**外部可观测的行为差异**才失败，
   且失败必须携带**反例对**。三题最后存活的候选却都是**外延相同**的函数
   —— A 的 `n >= 1` 与 `n > 0`（u64 上恒等）、C 的 `body_len <= 8388608` 与 `< 8388609`、
   B 的"通配臂"与"六个变体全列举"。没有任何输入能把它们分开，
   于是 `explore` 报"欠定 —— 补一条 example 让它们分开"（退出码 1）时，
   **它要人补的东西根本不存在**。这是实现比判据严、且把判据的一条前提踩空了：
   判据 A 从来没有要求"唯一的一份写法"。
   正确的出口是把结局分成三种（唯一存活 / 多存活**且有分歧** = 欠定 /
   多存活**且无分歧** = 未证分歧），第三种必须写明"判定只用了这些输入"——
   无分歧 ≠ 等价。登记为 P15，并作为一条 D0 偏差记进 §3 工具链。
   注意：等价本身是我按语言语义推的，工具里没有等价判定，我也没有 —— 这条只能算论证，不算测量。
2. **"首次通过率"这个指标在自产候选下没有信息量**（9/9 通过）。要它有意义，
   候选必须来自与出题人无关的模型；否则测的是我自己的自我一致性。
3. **"人只写意图 + 空实现"这份工件编不出来。** 占位实现体不引用参数，
   生成的 C 在 `-Werror=unused-parameter` 下直接失败（`droplet verify intent.dlt` 报的是
   `cc 失败：unused parameter 'v_n'`）。D0 里没有"未实现"这个标记，
   所以意图只能寄居在带实现的候选文件里。这解释了为什么 `intent.dlt` 的占位实现
   必须写成"用到参数但规则不全"（A 用 `n > 0`、C 用 `(if_match == prev) && (body_len > 0)`）
   —— 而它们确实被样例否掉了（A 否 1 条、B 否 2 条、C 否 2 条），"意图有牙齿"这一点在三个任务上都成立。
4. **`MISS` 有两类，工具现在不区分 —— 人会为第二类白补样例。**
   一类是**真缺口**，补一条样例就堵：A 的 `>= 1` → `> 1` 被新加的 `size_ok(1) == true` 抓住；
   C 的 4 处 MISS 全在 `prev == 0` 那道守卫上，补 `can_write(0, 0, 10) == false` 后
   `mutate: 2 处变异，0 处没被抓住`（三个候选都归零）—— 这一条我第一轮没补到，
   我先补的是上界那条，`MISS 4 → 4`，白补。
   另一类是**等价变异**：改动不可观测，任何样例都堵不上 —— B 里"把 `return false` 的分支体
   清空 / 删掉"共 12 处（通配臂 ×2 + 四个具名 false 臂 ×2 + c 的通配臂 ×2），
   函数返回值一模一样，`14 → 12` 之后再也降不下去。
   总账：**人补 6 条样例，3 条起效**（A 堵 1 处、C 堵 4 处、B 否掉 1 个候选），3 条无效
   （C 的第一条打偏、B 的另外两条动不了等价变异）。
5. **非数值参数的分歧，工具一条也抓不到。** B 的自动输入是 **0 条** —— 取值池只覆盖
   u64 / i64 / bool，`ApiError` 这类 sum 参数被排除（D0「候选收敛」第 ① 条边界）。
   结果：c 把 `Conflict` 判成可重试这件事，**只有靠人手写一条 `example` 才暴露**。
   这条边界在真实任务上的代价第一次有了具体形状。
6. **`verify` 的 `MISS` 只给位置，不给能翻面的输入。** 于是"补哪条样例"完全靠人从
   位置 + 变异种类反推。对比之下 `explore` 已经会按签名造边界输入 ——
   那条能力挪一半给 `verify`（对每处存活变异，在取值池里找一个能翻面的输入并报出来），
   人工成本就会从"猜"变成"挑"。登记为 P14。

## 5. 怎么重跑

```sh
cd <仓库根>
go build -o .build/droplet ./code/lang/cmd/droplet
for t in size_ok retryable can_write; do
  for f in a b c; do .build/droplet verify docs/validation/p6/$t/$f.dlt; done
  .build/droplet explore docs/validation/p6/$t/{a,b,c}.dlt
  .build/droplet verify docs/validation/p6/$t/intent.dlt   # 占位实现应被样例否掉
done
```

退出码：`verify` 有样例不成立或有变异存活 → 1；`explore` 存活多于一个 → 1。
`explore` 的输出会把"每条样例在每个候选上的 PASS/FAIL"并排列出，这就是分歧点名。

## 6. 这一份算不算 P6 的完成

**不算。** P6 要的是"方法在真实任务上成不成立"，而 §1 的偏置使它只能证明
**流程和工具有效、且方法有一个未处理的前提（等价候选）**。
按判据原样收口，结论应该是 NEXT 里那条预写判据的第三种结局 ——
"多数题在 3 轮内不收敛"，但**原因不是意图表达力不足**，
而是**工具的收敛判定比判据 A 严，且严在不可能满足的地方**。所以下一步分两半：

- **P15**：把 `explore` 的收敛判定改回判据 A 的口径（三分：唯一存活 / 有分歧 = 欠定 /
  无分歧 = 未证分歧并注明所用输入集）。这是 §7.8.3-1 的**实现偏差**，不是判据要改。
- **P14**：让 `verify` 对每处存活变异报出一个能翻面的输入（复用 `explore` 的取值池）。
- **P6 复跑**：候选换成作者从不可控模型取得的三份，其余流程与本题面不变，
  这样"首次通过率 / 收敛轮数 / 人补样例条数 / 人分钟数"才有意义。

本轮不动 `code/lang`：H8 仍 7993 / 8000（余量 7 行），用例 142。

## 7. 对照组：同一个服务直接用 C 写（v0.29）

### 7.1 这一节要证伪的是我自己

作者的问题很直白：AI 对 C 的训练已经够多了，为什么不直接用 C。
我上一轮的回答里有一条"这门语言把正确性从需要理解变成需要机械检查"，
但没查过这句话里的机械检查有几分是**语言**的功劳、几分是**任何语言 + 一份清单 + 一个检查器**就有的。
这一节就是去查这个，且默认结论可能否掉这门语言。

公平条件先摆明：

| 条件 | 做法 |
| --- | --- |
| 运行时 | 1472 行 `rt_*.c` **两组共用**，不算语言的功劳（HTTP 解析、鉴权、key 合法性、413、快照、commit 都在里面） |
| 编译参数 | C 侧用与生成物完全相同的 `-std=c11 -O2 -Wall -Wextra`，并额外单独试 `-Werror` |
| 判定 | 不是打印给人看的 17 行，是 `accept-c.sh` 里 **19 条断言**（原 17 条 + 「404 空 body」+「405 空 body」） |
| 对照组必须写到功能全对 | 先写一版自然的 C（15/19），再修正到 19/19；**四条纪律要在功能全对的 C 上试**，写坏的 C 说明不了"结构上做不到" |
| 同源偏置 | C 也是我写的。这一节测的是**机制有没有**，不是通过率 —— 与 §1 的偏置声明同一条性质 |

### 7.2 工件与基线

| 组 | 人写的行数 | 19 条断言 |
| --- | --- | --- |
| droplet | `contract.dlt` 64 + `main.dlt` 31 + `intents.dlt` 48 = **143** 行 → 生成 **247** 行 C | **19/19** |
| C 第一版 `service.c` | **195** | 15/19（挂 #7 #14 #17 #18） |
| C 第二版 `service2.c` | **201** | **19/19** |

C 第一版挂的四条不是随手写坏的样本：`dp_response` 只有一个 `status` 和一个 `body`，
"错误不携带表示"（D2/R2）在 C 里**没有落点**，写 C 的人自然会把 `{"error":"not found"}` 塞进 body，
于是运行时还给错误页推了 ETag（#18）。这是一条纪律在 C 里无处安放的实例 ——
但要说清：**它被 wire 断言抓住了**，因为那张表里恰好有"412/404/405 空 body"三条。

### 7.3 四条纪律逐条实测

**① 守卫落点（If-Match 不能按路由漏写）**

- C：把 `service2.c` 里 If-Match 那 7 行整块删掉 → `-Wall -Wextra -Werror` **全部通过**；
  跑表 **18/19**，只挂 #6（If-Match 不符却回 204）。
  更难看的是 **#7「412 空 body」照样通过** —— 响应已经不是 412，body 仍是 0 字节，**断言空过**。
- droplet：同形变异 = 从路由声明里删掉 `, precondition` →
  `E1: 写路由 PUT /v1/blob 必须显式表态：with precondition 或 without precondition: "理由" —— 沉默等于默认不做并发保护`（编译期失败）。
- 补测（这条最要紧）：droplet 里显式写 `without precondition: "理由"` → 编译过，跑表同样 **18/19、同样只挂 #6**，
  与无守卫的 C **一模一样**。
- ⇒ 语言的增益**不在运行期强度**：人一旦显式决定不保护，两边行为等价。
  增益只有一句话：**在 C 里"漏写"和"决定不写"是同一个状态，在这里不是。**

**② 外部触点可枚举（不能有环境读取 ambient）**

- C：5 个 `APP_*` 名不在 `getenv` 处，而在 `cfg_get("APP_ROOT", …)` 的调用点上 ——
  也就是说**光是"列出读了哪些环境变量"就取决于你怎么重构代码**。另有 1 处未声明读取（`DP_LOG_LEVEL`）。
  写了 **45 行**对账器（`surface-c.py` + `manifest.json`）：它精确报出
  "代码里有、清单没写 `['DP_LOG_LEVEL']`"，退出码 1。
- 它的上限（实测）：把同一处读取改成 `snprintf("%s%s%s", "DP_", "LOG_", "LEVEL")` 再 `getenv(nm)` →
  对账器报**三类全对得上、退出码 0**，而二进制照读（stderr 打印 `log level debug`）。
  ⇒ 基于文本模式的抽取会被**一次普通重构**击穿，不需要恶意。
- droplet：`cfg.loglevel`（未声明字段）→ `E1: Cfg 没有字段 loglevel`；要读就得进 `env`，
  进了 `env` 就出现在 `contract` 的 `envs` 节（5 个键，带 `var` / 默认值 / `required`）。
- 诚实的半句：共享运行时自己有 **3** 处 ambient 读取（`DP_SNAPSHOT_KEEP`、`DP_COMMIT_DEBOUNCE`、`DP_COMMIT_CMD`），
  这两组**一样不闭合**。闭合只覆盖人写的那 143 行（v0.32 起 206 行：多的 63 行是决定层与样例表）与生成的 247 行。
- ⇒ 差在"闭合是**结构性的**还是**模式性的**"。

**③ 可执行意图 + 变异**

- C 里决定不在这份文件里：`requires_auth` 落在 `rt_http.c:465` 的请求循环内，
  `create_ok` 落在 `rt_blob.c:356` 的返回值里。要让样例够得着，只能**手抄一份**
  （`decisions.h` + `decisions.c` 35 行，加执行器 `intent_c.c` 30 行）——**样例验的是复制品，服务跑的是原件，没有任何东西把守两者一致**。
- 把 `verify` 的两个算子（分支删除=清空 then；提前返回=删掉 return）逐处作用到 `decisions.c`：
  **8 处算子 → 6 个不同程序**（C 的 then 块只有一条语句时，两个算子落到同一处文本）。
  同一批 6 条样例的结果：droplet 编译参数下 **5 抓住 / 1 MISS**（C3：删掉末尾 `return true;`），
  但那 1 处编译器报 `warning: control reaches end of non-void function`；
  换 `-Werror` → **6/6**。droplet 侧同批：**6 处变异，0 处没被抓住**。
- ⇒ **这一条语言不占优**：C + 样例 + `-Werror` 拿到同样的变异覆盖率。
  语言剩下的唯一真差别是"样例写在被调用那一侧，不必复制实现"。
- 方法学事故，记下来：第一版变异脚本拿裸 `"    return false;"` 当锚点，
  匹配到了 6 空格那行的**后半截**，产出一个根本没碰 `create_ok` 的假变异并被当成 MISS。
  变异实验里最便宜的失败就是把假变异当发现 —— 脚本头部已把这条写成注释，锚点全部改成整块。

**④ 外部面可导出、可 diff**

- `droplet contract` 有四节：`boundaries / functions / tags / envs`。PUT 那一项里
  `success: 204`、`precondition: true`、`intents[]`（invariant 文本）、`idempotent` 都在，位置带 `path:line`。
- 去掉 `@no_content`（外部变更，204→200）→ `boundaries` 节 diff = **1 行**（`- "success": 204,`）。
  抽一个 helper（纯内部重构）→ `boundaries` 节 diff = **0 行**（`functions` 节 +22 行，另属一格）。
- C 只有源码文本这一种介质：同样两个改动 → **2 行 vs 14 行**，同类同形，
  审的人分不开"改了承诺"和"改了写法"。

### 7.4 对照组赢了一局，而且赢得对

实测（各自干净数据目录、同一个 key 连 POST 两次）：

| 二进制 | 第一次 | 第二次（key 已存在） | 契约里的 invariant |
| --- | --- | --- | --- |
| `blobd-lang` | 201 | **201** | "POST 只在 key 不存在时成功" |
| `blobd-c2`（手抄 C） | 201 | **409** | 同一条 |

根因：`main.dlt` 里 `fs.create(cfg.root, key)!` 把 `bool` 丢掉了 —— `create` 的语义是
"已存在返回 false，不是错误"（`rt_blob.c:371`），生成的 C 就是 `(void)(_t11.u.ok);`。
而这条 invariant：① 是散文，不进 oracle（§D.9）；② boundary 上的 example 也不被收集（P12）；
③ 19 条 wire 断言里没有"同一个 key POST 两次"这一条。
**三层全都没看见它。** 更刺的是 `code/webapi/intents.dlt` 里 `create_ok` 的 6 条样例全过、变异 0 漏，
与服务的真实行为**直接矛盾**，而工具从不比较这两者。

⇒ 这是本仓库对"人只审目标"目前最硬的一条反例：目标被写成字据、被抽成可执行谓词、全部通过，
**实现照样违反它**。拦到这件事的不是语言的四条纪律，是对照组里那句手写的 `if (!create_ok(exists))`。

### 7.5 结论

1. 四条纪律里 **①②④ 语言确有结构性增益**，但形态要说准：
   ① 让"沉默"不能成为一个决定；② 让闭合是结构性而非模式性的；④ 让承诺与写法分成两种介质。
   都不是"更强的运行期安全" —— ①的补测（显式 `without precondition`）与 C 无守卫版等价，就是这件事的证据。
2. ③ **语言不占优**。C + 样例 + `-Werror` 同样 6/6。谁的变异覆盖率更高这种比较，撑不起这门语言。
3. 所以"要不要一门语言"该由 **7.4** 决定：**声明的目标与跑着的实现之间有没有一条会失败的通路**。
   今天没有。缺的那块正是 **P12**，它从此不是一条改进项，是命题的空心部分。
4. 收回我上一轮的一句话：我把四条纪律当成命题成立的证据；对照实验显示它们最多是**必要条件**。
5. 方案 B（C + 清单 + 检查器）不是纸上谈兵 —— 45 行就拿到了枚举与对账（见 `c-control/OPTION-B.md`），
   但闭合性止于文本模式：要跨过 7.3-② 那个拼接名的例子，检查器必须落到语义层
   （libclang / 编译插件 / 静态分析框架），成本回到"写一个 front-end"的量级。
   这句话是本轮能给 B 的最强陈述，也是它能被否掉的方式。

### 7.6 怎么重跑（C 对照组）

## 8. 超集形态的实测（v0.30 建，v0.31 兑现"超集"，v0.32 补样例 oracle）

改判后的数字（决定依据见 SPEC §0.8）。对象：`code/sup/`，旗舰服务的 C 超集写法。

### 8.1 同一张表跑两种介质

| 编号 | 断言 | 超集 | 语言版（`.dlt`） |
| --- | --- | --- | --- |
| #1–#19 | 上一轮对照组那张表（错误空 body、204 无 Content-Length、405、412、413…） | 19 过 | 19 过 |
| #20 | 同一 key 连 POST 两次 = **409** | 过 | **挂（实际 201）** |
| #21 | GET 回来的字节 = 最近一次成功 PUT 的字节 | 过 | 过 |
| 合计 | | **21 过 / 0 挂** | **20 过 / 1 挂** |

#20 就是 D.10 里对照组赢我们那一局。#21 是 v0.30 新发现：上一轮那 19 条里**没有任何一条**
在验契约明写的这条 invariant，两种介质下一直未证（超集补为 #21，语言版仍缺，记 D0）。

### 8.2 破坏测试：11 项全被抓，0 假阴性

v0.31 起每条破坏都断言**是哪个工具、以什么诊断抓的**，构建日志留档
`.build/sabotage/<名>.log`；期望的模式不出现就整轮失败退出。这道工序是本轮补的：改的过程里
v0.30 的 S3/S7（以及本轮最初的 S8）一度因为注入代码少了 `#include <stdlib.h>` 而编译失败，
却被报告成"符号审计抓住了"——那是假绿。归因写对之后，真实结果仍是 9/9。
v0.32 加 S10/S11（样例表带进来的新口子），实测 **11 抓住 / 0 假阴性**。

| 编号 | 破坏动作 | 抓它的工具 |
| --- | --- | --- |
| S1 | 路由表里删掉一行（实现留着） | 编译器 `-Wunused-function` + `-Werror` |
| S2 | 表里列一个不存在的实现 | 编译器 `used but never defined` |
| S3 | 读没声明的环境变量（合法 C 写法，自带 `<stdlib.h>`，编译通过） | 符号审计：用户 `.o` 里 `U getenv` |
| S4 | 目标谎报不存在的断言号 #99（构建照过） | `contract-sup.py` 退出码 1 |
| S5 | 从验收表里删掉断言 #20 | `contract-sup.py` 退出码 1（`create_once` 失去证明） |
| S6 | 把"丢弃 create 的 bool"塞回**决定层** `dp_decide.c` | 两条：oracle 样例 #2 翻面 **且** `accept-sup.sh` #20 挂 —— 只红一条按归因不全处理 |
| S7 | `snprintf` 拼出未声明的环境变量名再读 | 符号审计：拼名只产生字符串，符号表只看名字 |
| S8 | 不碰任何宏，按 libc 正规名字读没声明的变量（原 E1） | 符号审计 `U getenv` |
| S9 | `extern char **environ`，一次 `getenv` 都不写（原 E6） | 符号审计 `U environ` |
| S10 | 把 create 的决定就地写回胶水层 `dp_sup.h`（绕开被样例覆盖的那份，E9） | 接线检查：`nm -u blobd.o` 里不再有 `dec_create_result` |
| S11 | 把端口区间就地抄回机制 TU `dp_cfg.c`（**行为完全等价**，21 断言照过） | 接线检查：`nm -u dp_cfg.o` 里不再有 `dec_port_usable` |

### 8.3 C 兼容性实测：v0.30 挂，v0.31 过

v0.30 标题写着"本项目是 C 的超集"，实测证明那句话不成立：`dp_sup.h` 末尾那行
`#define getenv(name) dp_env_not_declared_in_DP_ENVS(name)` 让一份合法 C11 程序在 include
本层之后**编译失败** —— 那是 incompatible extension。v0.31 删掉它，未声明效果的检查改用
构建后的符号审计。`code/sup/compat-sup.sh` 就是量这件事的：

| 项 | 测试内容 | v0.30 | v0.31 |
| --- | --- | --- | --- |
| p1 | `stdlib.h` + 一次 `getenv`：无本层 / 有本层两种口径都要编得过、输出一致 | 有本层编不过 | **过**（两口径输出一致） |
| p2 | C11 特性堆：`_Generic`、复合字面量、`_Static_assert`、匿名联合体、VLA、指定初始化 | 过（未 include） | **过** |
| p3 | 手工内存、旧式 `main()`、可变参宏、`goto` 标签 | 过 | **过** |
| probe | 一个 include 本层、在 `main` 里按 C 常理调 `getenv` 的程序 | **编译失败** | **编译通过**（改由审计抓） |
| 审计 | probe 的用户 `.o` | —（宏在编译期挡） | **红**：构建失败 |

合计 **5 过 / 0 挂**。

**交换要记账**：v0.30 是编译器现场拒绝，代价是把合法 C 一起拒绝；v0.31 是合法 C 全过，
代价是检查从编译期挪到构建脚本。于是新增 E7（绕开 `build.sh` 直接 `cc` 就绕开审计）和
E8（`dlopen` + `dlsym("getenv")` 在运行时才解析，`nm -u` 看不见）。两个新口记 §8.4，不藏。

### 8.4 逃逸口

| 编号 | 动作 | v0.30 | v0.31 |
| --- | --- | --- | --- |
| E1 | 不碰宏，按 libc 正规名字读没声明的变量 | 构建成功（宏靠 `#undef` 挡） | **已闭合**（S8，符号审计不看文本） |
| E2 | 实现改非 `static` / 拆第二个 TU | 构建成功 | **仍开着**：`-Wunused-function` 只守单 TU，跨 TU 信息不在链接前 |

E9 只在 v0.32 之后存在，它随 §8.6 的 oracle 一起来、也在同一轮被接线检查闭合（S10、S11），

### 8.6 样例 oracle：超集侧补上的那件唯一缺的能力（v0.32 / P18 ①）

P18 的平价清单里，超集形态缺的只有一件：`droplet verify` 那种"封闭样例当可执行 oracle +
机械变异"。这一节就是把它搬进 `code/sup/`，并且**避开对照组输掉的那个坑**。

口径与设计记录在 SPEC §0.8.6（第四张表 `DP_EXAMPLES`）；未覆盖的面记 D0-DEVIATIONS §3
「样例 oracle 只覆盖纯决定」。

**坑是什么**：§7.3 ③ 记的原文是"样例验的是复制品，服务跑的是原件，没有任何东西把守两者一致"。
C 对照组为了让样例够得着决定，把 `requires_auth` / `create_ok` 手抄成 `decisions.c` 35 行 ——
于是那张样例表证明的是抄本。本轮若照抄这个做法，超集侧的 oracle 就是同一个错误的第二次发生。

**这一版怎么把"是不是同一份"变成可失败的检查**：决定搬进 `dp_decide.c`（18 行，用户所有），
`dp_sup.h` 的 `dp_created()` 与 `dp_cfg.c` 的 `dp_load_port()` **调它**，oracle 二进制
**链接同一份对象**。一致性不靠声明，靠符号表：`build.sh` 链接前要求

```
接线绿：blobd.o 引用了被样例覆盖的决定（dec_create_result）
接线绿：dp_cfg.o 引用了被样例覆盖的决定（dec_port_usable）
```

任何一侧把决定就地抄回调用点，`nm -u` 立刻看不见那个符号，构建红。破坏测试 S10、S11
就是专门来验这条会不会说谎的，两条都红在"接线红"上（§8.2）。

**工件与归属**（v0.32 新增）：

| 文件 | 行 | 归属 | 作用 |
| --- | --- | --- | --- |
| `dp_decide.h` | 45 | 用户 | 两个纯决定的声明 + `DP_EXAMPLES` 7 行样例表 |
| `dp_decide.c` | 18 | 用户 | 两个决定的实现 —— 服务链接的就是这一份 |
| `dp_oracle.c` | 92 | 机制 | 把 `DP_EXAMPLES` 用 X-macro 两遍展开成执行器（`--list` / `--only N`） |
| `oracle-sup.sh` | 67 | 工具 | 编译 -> 审计 -> 逐条一个进程跑 |
| `mutate-dec.sh` | 149 | 工具 | 把 `verify` 的两个算子搬到决定层，逐条断言预期结局与归因 |

**实测（2026-11-01）**：

| 项 | 结果 |
| --- | --- |
| 样例 oracle | **7 条 / 7 过 / 0 挂 / 0 崩溃** |
| 决定层变异 | 8 个变异体：**5 抓住 / 2 MISS（等价变异）/ 1 编译期响 / 0 归因不符** |
| 干净参照 | 先跑，参照不绿则整轮结论作废（本轮绿） |
| C 兼容性（§8.3） | 仍 **5 过 / 0 挂**：`dp_sup.h` 多 include 一个头，语料与判定一行没改 |
| 锚点唯一性 | 每个锚点 `count == 1`，不满足直接退出 —— 防止把没碰到目标的假变异当发现 |
| 崩溃隔离 | 一条样例一个进程；本轮 0 条崩溃，但这条通道是实测过的（`--only` 未知编号也照样红） |

**三种介质的变异覆盖放在一起看**（口径不同，只放同一张表不折算）：

| 介质 | 变异体数 | 样例抓住 | 编译器补刀 | 没被抓住 |
| --- | --- | --- | --- | --- |
| `droplet verify`（语言版 `intents.dlt`） | 6 | 6 | — | 0 |
| C 对照组（`mutate-c.sh`） | 8 算子 → 6 程序 | 5 | `return true;` 那处由 `-Werror` 补，合计 6 | 0 |
| 超集决定层（本轮 `mutate-dec.sh`） | 8 | 5 | 空函数体那处由 `-Werror` 补 | **2**（`x >= 1` 改成 `x != 0`、`err != 0` 改成"大于 0 或小于 0"，都是等价变异） |

那两个 MISS 是我**人工判定**为等价的（无符号与非零判断在全部取值上同外延），工具并没有证明它们等价
—— 这正是 §4 第 2 条记过的坑：`MISS` 分真缺口与等价变异，而工具不区分二者，人会为后者白补样例。
这里把它照实标成"等价变异（人工判定）"，不折算成"抓到了"。

**边界，不许漂**：
1. 住的进 oracle 的只有**纯决定**（函数体里只有条件与常量）。鉴权在 `rt_http.c:465`、
   版本前置在 `rt_blob.c` / `rt_ver.c`，都在两种介质共用的那 1472 行运行时里，oracle 链接不到、
   也不该链接 —— 那部分样例覆盖仍是语言的 `verify` 在做（记 D0）。
2. 只有 2 个决定、7 条样例。这是**最小可用版**，不是完整覆盖；`DP_EXAMPLES` 里新增一行就要求
   对应决定存在，否则 oracle 编译期就红（X-macro 直接展开调用）。
3. `explore`（多候选对比）在超集侧还没有对应物，P18 的其余三项也没做。
