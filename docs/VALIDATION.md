# VALIDATION：这些数字是跑出来的

> 这份文档只记**实测**：怎么跑、跑出什么、以及这些数字不能证明什么。
> 每条命令都能在干净 clone 上重跑。

## 1. 怎么跑

```sh
sh code/sup/compat-sup.sh                          # 5 条：合法 C 在"无本层/有本层"两种口径下输出一致
sh code/sup/build.sh sup                           # 编译 -> 符号审计 -> 接线检查 -> 链接
sh code/sup/oracle-sup.sh                          # 19 条封闭样例，一条一个进程
sh code/sup/mutate-dec.sh                          # 13 个变异体，逐条断言结局与归因
sh code/sup/accept-sup.sh "$PWD/.build/sup/blobd" 18880 sup   # 30 条 wire 断言
python3 code/sup/contract-sup.py .build/sup/blobd   # 5 路由 / 5 配置 / 18 目标 / 19 样例对账
python3 code/sup/req-check.py .build/sup/blobd     # 16 源句 / 19 条款 / 30 断言 / 19 样例 / 18 目标的登记链
python3 code/sup/req-check.py .build/new/blobd     # 有“新增”条款时自动去建基线（旧实现 + 当前题面）再核先红后绿
python3 code/sup/req-check.py .build/new/blobd --no-baseline   # 快速回路：不启服务，跳过基线那一层
sh code/sup/freeze.sh --check .build/sup/blobd     # 题面 12 项（含 5 份译稿）与 req/FROZEN 一致
python3 code/sup/mutation-score.py --binary .build/sup/blobd   # L 30 表自检 + E 19 样例自检 + S 25 实现变异 + 台账对账
sh code/sup/surface-budget.sh                      # 必读面字节 / token 预算
sh code/sup/compare-sup.sh --self-test             # 候选比较：唯一 / 无解 / 歧义，4 条自检
sh code/sup/firstpass.sh --self-test               # 首次成功率量尺，3 条自检（不产生模型数字）
sh code/sup/maint-cost.sh                          # 三种改动的文件数 / +/- 行数
sh code/sup/lang-check.sh .build/check/blobd       # 登记语言四段：码表对账 + 码活性 + 与 req/ 等价 + 定义预算
sh code/sup/sabotage-sup.sh 18900                  # 23 条破坏，每条必须被具体工具抓住
sh code/sup/check.sh --full                        # 作者/维护回路：一条命令一个退出码（14 项）
sh code/sup/brief.sh .build/briefpack              # 题面包：surface + contract + req/ 译稿，不含实现

sh code/sup/report.sh .build/check/blobd --accept 18881  # 人类验收页
sh code/sup/lab/make-packet.sh /tmp/lab/packet     # 实验题面（两条仓库里不存在的决定）
```

再跑同一张 30 断言表。

### 2.1 接口承诺（30 条断言钉住的那些）

| # | 承诺 |
| --- | --- |
| 1–3 | 探活不鉴权；无 token / 错 token 一律 401 |
| 4–7 | ETag 由 body 推导；`If-Match` 不符 412 且 body 为空；符合则放行 |
| 8–9 | 204 不带 `Content-Length`、不带 body |
| 10–12 | POST 只在 key 不存在时成功（201 空 body）；同一 key 再 POST = 409；清单来自目录 |
| 13–17 | 404 / 400 / 405 的映射；错误响应不带表示 |
| 18–19 | 405 无 ETag；9 MiB body → 413 |
| 20–21 | 同一 key 连 POST 两次 = 409（丢 bool 那一局）；GET 回来的字节 = 上次 PUT 的字节 |
| 22–24 | 覆盖写前留快照（3 份）；4 次成功写入 = 4 条提交；清单 3 个 key 来自目录本身 |
| 25–26 | 配了 token 时，错 token / 没带 token 一律 401（鉴权判断在 `dp_decide.c`，样例 #12–#16 覆盖同一份） |
| 27 | 清单 body 精确等于 `{"keys":["demo","second","third"]}`：对象外壳 + 字典序（v0.36 的一句新需求 `S14`/`R17`） |
| 28 | 带 body 的成功响应声明 `Content-Type: application/json`（`S15`/`R18`，散文没写过，A/B 实验里只有读译稿的臂提出来） |
| 29 | 空目录也是合法对象：`{"keys":[]}`（`S14`/`R17` 的第二条判据，把 `GAP G8` 从“没判据”变成“已闭”） |
| 30 | 数据目录不可用（这里指指向一个普通文件）时**拒绝启动**并留下诊断（`S16`/`R19`；唯一一条不问 HTTP 的断言，闭合 `GAP G9`） |

### 2.2 候选比较说明了什么

`compare-sup.sh` 的输入是 N 份完整 `dp_decide.c`。自检里有一个关键用例：把端口判断改写成
`x != 0ul && x < 65536ul`（与原件在 `unsigned long` 上同外延），19 条样例全部通过 ——
于是工具报**歧义**。这不是工具失败，而是结论：样例没有把这两份实现分开，交付哪一份都是猜。

所以“唯一”只在一个明确范围内成立：**样例覆盖到的行为**。这个范围写不出来时，工具不会替你补。

## 3. 两次真实的失败（留档，不删）

第一次把这套表放进 CI，`latest` job 上 #23 只数到 3 条提交，`srv.log` 里是
`fatal: cannot lock ref 'HEAD'`。

根因不是表写错：运行时对**每次**成功写入并发拉起提交子进程（`DP_COMMIT_DEBOUNCE=0` 不合并），
四个 `git commit` 抢同一个 ref 锁，输的那条静默丢失。本机跑得快、碰巧串行，从没显形。

修法：把 `DP_COMMIT_CMD` 写成 `flock <锁文件> sh <脚本>`，并把轮询窗口从 3 秒放宽到 10 秒。
**#23 仍然断言“恰好 4 条”** —— 排队不是放宽。同一条坑写进了部署样例与 NEXT。

第二次显形在 ASan 构建上：同一条 #23 稳定 3/4，`srv.log` 里是 `nothing added to commit`。
根因和第一次不同 —— flock 排开了 ref 锁，排不开内容：两次写入挨得太近时，两个提交子进程
拿到锁看到的是同一份内容，先拿到锁的那次提交为空，快照被合并。修法在表里：每次成功写入后
等它自己的提交落地，再发下一次写（`wait_commits`），断言仍然只认“恰好 4 条”。
这不是纯粹的测试补丁：`DP_COMMIT_DEBOUNCE=0` 且写入快于提交时，快照确实会合并；
生产口径应当开 debounce（见 `blobd.env.example`）。

## 4. 这些数字不能证明什么

1. **覆盖面窄**。oracle 覆盖 5 个纯决定（19 条样例），但读写、快照轮转、提交调度仍在运行时；
   “19/19 全过”不等于“服务正确”。
2. **wire 断言是人写的**。30 条之外的错误不会自己冒出来；漏掉的测试就是没有的测试。
   `TRANS` 的证据列与 `GAP` 的“不闭”就是为了让“漏掉的”至少有个名字。
3. **变异有 2 个 MISS**。我判定它们与实现等价（无符号与非零判断同外延），工具并没有证明这一点。
4. **运行时在检查面之外**。1468 行共享 C 没有样例、没有变异；它出问题只能靠 wire 断言兜。
5. **没有长稳结论**。`soak.sh` 只跑过压缩时间自测（60 秒级），72 小时那条线仍是空的。
6. **首次正确率只有一个很小的数**。决定层 n=3、pass@1=3/3，题面由人写、模型同族、首次提交口径；
   不能外推成“AI 能写这个服务”。完整服务与人类维护者仍然没有测量（EXPERIMENT §5）。
7. **必读面的 token 数是估算**。ASCII 4 B/token、非 ASCII 3 B/token；换分词器会变。
   它是回归护栏，不是“AI 需要读这么多”的因果结论。
8. **维护成本只数局部性**。三个脚本化改动都在小面上完成；这不代表任意改动都便宜：
   实测一次跨层维护（405 -> 501）是 5 文件 / 18 个 +/- 行，因为映射住在运行时，
   样例碰不到，只能靠 wire 断言与目标措辞同步（EXPERIMENT §2）。
9. **需求登记只对齐“已经写下的条款”**。需求文档本身漏写、写错、或把两件事混成一条，
   五道门都发现不了；`req-check` 证明的是“条款与证据的链子没断”，不是“条款完整”。
   翻译层（`TRANS`/`AMBIG`/`--baseline`）能把“抄现状”“默默选一种读法”“把表达不了的写成断言”
   变成红，但它验的是**这次译得对不对得上旧实现**，不验译文本身。
10. **变异覆盖 30/30 只覆盖 25 种已知错法**。它证明每条断言至少能被一种有意义的改动弄红，
    不证明断言集合覆盖了所有可能的错法。S 变异由人列清单，清单之外的新错法仍然没有证据；
    `S01`/`S07` 两条甚至还没被任何条款的反例认领（工具只提示，不判红 —— 因为它们代表的是
    “实现里坏一下总得有人管”，而不是一条写下来的语义差异）。
11. **冻结保护的是文件与契约哈希**。它拦“改题后再走提交口/快速回路”；如果有人完全绕过
    这些命令直接部署二进制，冻结不拦（与 §5 的 E7 同类口子）。

## 5. 翻译层端到端：一句新需求走完五道门（2026-11-02，v0.36）

文本需求只给一句：**“清单响应必须是一个 JSON 对象，顶层键 `keys`，值是按字典序排列的字符串数组。”**
下面每一步都是实际跑过的命令与看到的输出。

| 步 | 命令 | 看到什么 |
| --- | --- | --- |
| 1 源句 | 手写 `req/SRC.md` | 追加 `S14`；此前 13 句冻结不动 |
| 2 条款 | `req/REQ.tsv` 加 `R17`，源句 `S14`，类型 `新增`，目标 `list_envelope`，断言 `27` | 与 16 条 `回归` 条款并排 |
| 3 译法 | `req/TRANS.tsv` 加 `R17` 行；`req/AMBIG.tsv` 加 `A2`（“字典序”= 字节序，已定） | 排除栏写明不约束空白/转义；反例栏写“只查前缀会漏数字数组” |
| 4 题面 | `accept-table.sh` 加 `ck 27`；`DP_GOALS` 加 `list_envelope` | 27 条断言、16 条目标 |
| 5 基线先红 | `python3 code/sup/req-check.py .build/envelope-src/blobd --baseline .build/baseline-blobd --port 18600` | `回归 16 条全绿；新增 1 条在基线上为红`（旧实现回裸数组） |
| 6 换题 | `freeze.sh --check` 先红（验收表、契约、5 份译稿都不在旧哈希里）-> 人类 `freeze.sh --update` | `题面冻结：12 项一致` |
| 7 实现 | `dp_blob_list` 输出 `{"keys":[…]}`，空目录回 `{"keys":[]}` | 只改运行时一个函数 |
| 8 验收 | `accept-sup.sh <新二进制> 18601` | `27 过 / 0 挂`，`#27 -> {"keys":["demo","second","third"]}` |
| 9 变异 | `mutation-score.py --binary <新二进制> --floor 24` | `L 27/27；S 22/22；覆盖 27/27`，`S21`（退回裸数组）与 `S22`（排完再倒序）都恰好红 `#27` |
| 10 一页 | `report.sh <二进制> --accept <端口>` | `R17 S14 新增 断言 #27 -> 绿`；页脚 `源句 14 → 条款 17（回归 16 / 新增 1）` |

三个只有跑了才会说出来的事实：

1. **“按字典序”这条翻译本来是错的**。`dp_blob_list` 早就 `qsort` 过了 —— 如果照原文直接登记成
   一条独立断言，它在基线上就是绿的，`--baseline` 报“新增条款在基线上全绿”，把这条“抄现状”的
   翻译挡在实现之前。真正没做到的是外壳。这一条不是事后诸葛：它是这一层设计时担心的第一个陷阱，
   在这一轮真的踩到了。
2. **精确 body 比结构检查更省事也更狠**。`ck 27` 直接比整串字节。前缀或“是 JSON 对象”这类检查
   会被 `{"keys":[1,2,3]}` 骗过去；写进 `TRANS` 的反例栏之后，这个选择不再是随手写的断言。
3. **换题是一个动作**。第 6 步的红不是失败 —— 它证明 `req/` 里的译稿确实被算进题面：
   改译稿而不重新冻结，提交口直接拒。

不能证明的：这轮验的是“**这一句**译成一条会红的检查”，不是“这句需求翻译得最好”。
`AMBIG` 里两条都标了“已定”，但那是人的判断，工具只检查它有没有被写下来。

## 6. v0.37：把上一轮留下的两只“手”变成门（2026-11-02）

上一轮的五道门里，有两处实际上靠人自觉：`--baseline` 得有人记得跑，`TRANS` 的反例列只是句话。
这一轮把它们改成会红的东西，并把 `GAP` 从空表变成有状态的账。

### 6.1 先红后绿：从一次手跑到一道门

`req/BASELINE` 记一个 commit（换题时 `freeze.sh --update` 钉的是**此刻的 HEAD** = 换题前那道题的实现；
已存在就不覆盖 —— 一轮里反复改译稿不该把基线换成“已经做完的这版”）。`req-check.py` 看见有 `新增`
条款就自己调 `baseline-sup.sh`：

```sh
sh code/sup/baseline-sup.sh 89a310fd reqbase        # 末行是旧二进制的路径
python3 code/sup/req-check.py .build/check/blobd    # 登记 + 基线核对，一条命令
```

看到的输出（本轮实测）：

```
基线来源：基线 89a310fd：旧实现 + 当前题面
基线核对（先红后绿）：回归 18 条全绿；新增 1 条在基线上为红
```

三个设计细节，都是踩过才知道要写的：

1. **只覆盖题面，不覆盖实现**。`git archive <基线>` 出旧树，再按 `freeze.sh` 的 `FILES` 清单
   覆盖验收表 / 声明头 / 5 份译稿与契约相关文件；`blobd.c`、`dp_decide.c`、`rt_*.c` **绝不覆盖** ——
   否则就是拿新实现验新实现，基线门自证。
2. **构建要缓存**。旧树按 `sha + FILES 的 cksum` 打标（`.baselined`），题面没变就复用上次构建
   （~0.1 s），变了或传 `--force` 才重建（~10 s）。不然每次 `req-check` 多 10 秒，一天之后一定有人加 `--no-baseline`。
3. **换题时类型要迁移**。上一轮的 `新增` 这一轮必须改成 `回归`，否则基线上它早已实现 → 全绿 → 门红着说
   “新增条款在基线上全是绿的”。本轮 `R17` 仍是 `新增`（`#29` 在基线上红），`R18`/`R19` 登记成 `回归`
   （`#28`/`#30` 在基线上就绿 —— 实现早就在做这两件事，只是没人写过它）。
4. 浅 clone 导不出基线（CI 默认）会在这一层报**假红**，所以 `ci.yml` 的 checkout 改成 `fetch-depth: 0`；
   逃生口 `--no-baseline`（快速回路用，`check.sh --full` 与 CI 仍跑全量），破坏测试 #18 验“基线换成 HEAD
   时必须报自证”。

### 6.2 反例台账：`TRANS.tsv` 第六列交给机器对账

`TRANS` 从五列变六列，第 6 列是**证据**，三种编号混写：

| 写法 | 含义 | 谁验 | 本轮结果 |
| --- | --- | --- | --- |
| `S<n>` | 这条反例对应 `mutation-score.py` 的第 n 号实现变异 | 实测必须弄红**本条款声明的**某条断言（红在别处不算） | 23 个编号、17 条条款，实测全对 |
| `E<n>` | 这条反例对应 `DP_EXAMPLES` 第 n 号样例 | 样例必须在 E 相活着，**且本条款必须声明它** | 9 个编号、4 条条款（`R11`/`R14`/`R15`/`R16`），实测全对 |
| `-` | 这一条反例不认领任何编号 | 反例写“无（译法与原文同宽）”时必须是 `-`；写了真反例又只有 `-`，就必须有一条 `GAP` 且编号被反例点名 | 2 条（`R1`/`R10`），都是前者 |

实测口径（`python3 code/sup/mutation-score.py --binary .build/check/blobd`）：


`req-check.py` 那边同一件事的静态一半也绿：`R13` 若把证据改成 `S99`（不存在的变异）-> 红
（“`mutation-score.py` 里没有这条变异”，破坏测试 #20）；认领了 `E<n>` 却没在 `REQ.tsv` 的“样例”栏
声明它 -> 红。

这两条只提示不判红是有意的：`S01`（路由表里删一条路由）与 `S07`（配置默认值改一个字符）不是“某个
中文句子被译坏了”，是实现里坏一下总得有人管。写成条款反而会把台账变成凑数。

同时 E 相是这一轮新加的：`req-check` 管“声明有没有对上”，E 相管“样例本身是不是真判据” —— 19 条样例
逐条把期望取反，必须恰好挂它自己。**没有 E 相之前，`E<n>` 这种证据没法验**，所以我先加相再收列。

### 6.3 `GAP` 的三态：不闭不是删掉

`GAP` 上一轮是空的（0 行），原因写在表头：**没人去看 `TRANS` 反例列里那些“未断言，已知边界”** ——
写在私人笔记里等于没写。这一轮把状态收成三种：

- `未闭` = 挡路，`req-check` 直接红；
- `不闭` = 承认是当前口径下的边界，不挡路，但**必须出现在那条条款的反例文本里**（编号被引用），
  于是它在验收页上一眼能看见；
- `已闭` = 曾经没判据、现在有了，闭合它的断言/样例编号要写进文本。

本轮 9 行：`G1–G7` 不闭（快照内容、注册表文件、提交内容、500 带 body、随机 ETag、只测 DELETE、
只测一种非法 key），`G8`/`G9` 已闭（`#29`、`#30`）。`report.sh` 的页脚把这三态分开数：

```
歧义 4（未定 0）；缺口登记 9（未闭 0 / 不闭 7 / 已闭 2）
不闭的边界：G1 R3 …（每条一行，验收页上直接可读）
```

破坏测试 #19 验的就是状态不能口头漂移：把 `G1` 的“不闭”改成“未闭” -> `req-check` 报 `未闭：`。

### 6.4 这一轮的 A/B 没有正差异，但有两条账

12 份实现、两臂全对、0 次分岔 —— 译稿层“让实现更正确”这一条**没测出来**（EXPERIMENT §3.3）。

### 6.5 顺带：`GAP` 变有内容之后，题面包预算成了一个真决定

`brief.sh` 的包 = surface 5 份 + `req/` 5 份 + 契约 + TASK.md，不含任何实现。v0.36 装进译稿时

所以这里做的是显式决定而不是漂移：提到 **14,000**（`brief.sh` 里写了来源与理由），同时留一句实话 ——
