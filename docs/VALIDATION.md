# VALIDATION：这些数字是跑出来的

> 这份文档只记**实测**：怎么跑、跑出什么、以及这些数字不能证明什么。
> 每条命令都能在干净 clone 上重跑。

## 1. 怎么跑

```sh
sh code/sup/compat-sup.sh                          # 5 条：合法 C 在"无本层/有本层"两种口径下输出一致
sh code/sup/build.sh sup                           # 编译 -> 符号审计 -> 接线检查 -> 链接
sh code/sup/oracle-sup.sh                          # 19 条封闭样例，一条一个进程
sh code/sup/mutate-dec.sh                          # 13 个变异体，逐条断言结局与归因
sh code/sup/accept-sup.sh "$PWD/.build/sup/blobd" 18880 sup   # 26 条 wire 断言
python3 code/sup/contract-sup.py .build/sup/blobd   # 5 路由 / 5 配置 / 15 目标 / 19 样例对账
sh code/sup/surface-budget.sh                      # 必读面字节 / token 预算
sh code/sup/compare-sup.sh --self-test             # 候选比较：唯一 / 无解 / 歧义，4 条自检
sh code/sup/firstpass.sh --self-test               # 首次成功率量尺，3 条自检（不产生模型数字）
sh code/sup/maint-cost.sh                          # 三种改动的文件数 / +/- 行数
sh code/sup/sabotage-sup.sh 18900                  # 14 条破坏，每条必须被具体工具抓住
```

ASan+UBSan：把 `build.sh` 里的 `cc` 换成 `cc -g -fsanitize=address,undefined` 同口径编译，
再跑同一张 26 断言表。

### 2.1 接口承诺（26 条断言钉住的那些）

| # | 承诺 |
| --- | --- |
| 1–3 | 探活不鉴权；无 token / 错 token 一律 401 |
| 4–7 | ETag 由 body 推导；`If-Match` 不符 412 且 body 为空；符合则放行 |
| 8–9 | 204 不带 `Content-Length`、不带 body |
| 10–12 | POST 只在 key 不存在时成功（201 空 body）；同一 key 再 POST = 409；清单来自目录 |
| 13–17 | 404 / 400 / 405 的映射；错误响应不带表示 |
| 18–19 | 405 无 ETag；9 MiB body → 413 |
| 20–21 | 同一 key 连 POST 两次 = 409（丢 bool 那一局）；GET 回来的字节 = 上次 PUT 的字节 |
| 22–24 | 覆盖写前留快照（3 份）；4 次成功写入 = 4 条提交；清单 3 个 key 来自目录本身 |
| 25–26 | 配了 token 时，错 token / 没带 token 一律 401（鉴权判断在 `dp_decide.c`，样例 #12–#16 覆盖同一份） |

### 2.2 候选比较说明了什么

`compare-sup.sh` 的输入是 N 份完整 `dp_decide.c`。自检里有一个关键用例：把端口判断改写成
`x != 0ul && x < 65536ul`（与原件在 `unsigned long` 上同外延），19 条样例全部通过 ——
于是工具报**歧义**。这不是工具失败，而是结论：样例没有把这两份实现分开，交付哪一份都是猜。

所以“唯一”只在一个明确范围内成立：**样例覆盖到的行为**。这个范围写不出来时，工具不会替你补。

## 3. 两次真实的失败（留档，不删）

第一次把这套表放进 CI，`latest` job 上 #23 只数到 3 条提交，`srv.log` 里是
`fatal: cannot lock ref 'HEAD'`。

根因不是表写错：运行时对**每次**成功写入并发拉起提交子进程（`DP_COMMIT_DEBOUNCE=0` 不合并），
四个 `git commit` 抢同一个 ref 锁，输的那条静默丢失。本机跑得快、碰巧串行，从没显形。

修法：把 `DP_COMMIT_CMD` 写成 `flock <锁文件> sh <脚本>`，并把轮询窗口从 3 秒放宽到 10 秒。
**#23 仍然断言“恰好 4 条”** —— 排队不是放宽。同一条坑写进了部署样例与 NEXT。

第二次显形在 ASan 构建上：同一条 #23 稳定 3/4，`srv.log` 里是 `nothing added to commit`。
根因和第一次不同 —— flock 排开了 ref 锁，排不开内容：两次写入挨得太近时，两个提交子进程
拿到锁看到的是同一份内容，先拿到锁的那次提交为空，快照被合并。修法在表里：每次成功写入后
等它自己的提交落地，再发下一次写（`wait_commits`），断言仍然只认“恰好 4 条”。
这不是纯粹的测试补丁：`DP_COMMIT_DEBOUNCE=0` 且写入快于提交时，快照确实会合并；
生产口径应当开 debounce（见 `blobd.env.example`）。

## 4. 这些数字不能证明什么

1. **覆盖面窄**。oracle 覆盖 5 个纯决定（19 条样例），但读写、快照轮转、提交调度仍在运行时；
   “19/19 全过”不等于“服务正确”。
2. **wire 断言是人写的**。26 条之外的错误不会自己冒出来；漏掉的测试就是没有的测试。
3. **变异有 2 个 MISS**。我判定它们与实现等价（无符号与非零判断同外延），工具并没有证明这一点。
4. **运行时在检查面之外**。1468 行共享 C 没有样例、没有变异；它出问题只能靠 wire 断言兜。
5. **没有长稳结论**。`soak.sh` 只跑过压缩时间自测（60 秒级），72 小时那条线仍是空的。
6. **没有 AI 首次正确率的数字**。本轮补上了量尺（`firstpass.sh`）与候选比较（`compare-sup.sh`），
   但仓库里没有模型在环，没有候选序列可喂。所以这张表里没有 pass@k 的数 —— 只有量尺的自检。
7. **必读面的 token 数是估算**。ASCII 4 B/token、非 ASCII 3 B/token；换分词器会变。
   它是回归护栏，不是“AI 需要读这么多”的因果结论。
8. **维护成本只数局部性**。三个脚本化改动都在小面上完成；这不代表任意改动都便宜，
   例如改路由鉴权策略会同时牵动表、断言与目标措辞。
