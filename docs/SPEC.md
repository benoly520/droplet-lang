# Droplet —— 面向 AI 的服务端语言设计草案

> **状态**：v0.1 提案草案，未实现。本文档是立项与评审用的规范底稿。
> **语言名**：Droplet（仓库 `droplet-lang`）。
> **命题**：一门从零开始的服务端语言，第一读者是 AI 编码代理，第一维护者是人。
> **目标**：显著降低 AI 生成服务端代码的错误率，且**不依赖为它重新训练或微调模型**。
> **延伸目标**：跨平台（全 OS + WASM），并保留向裸机/嵌入式延伸的设计空间。

## 1. 定位与命题

### 1.1 一句话定位

**一门为"机器写、机器验、人读"设计的服务端语言**：把正确性从"需要理解"变成"需要机械检查"，把 AI 的失效面从"无限语义空间"压缩到"有限可枚举的结构事实"。

### 1.2 三个受众，优先级明确

| 受众 | 传统语言排序 | 本语言排序 |
| --- | --- | --- |
| AI 编码代理 | 第三（语言为人设计，工具也为人设计） | **第一** |
| 维护者（读代码、审代码、改代码的人） | 第一 | **第二** |
| 语言律师 / 特性探索者 | 第二 | **不服务** |

这个排序会体现在具体决策上：宁可牺牲"写法优雅/表达力强"，也要保住"签名可判定"和"错误可定位"。

### 1.3 与现有方案的差异

| 方案类型 | 代表 | 局限 | 本语言的差异 |
| --- | --- | --- | --- |
| 现有语言 + 严格 lint / 子集规范 | tsconfig strict、golangci-lint、clippy | 只能提醒与改写，不能改变类型系统的表达力；规则可被抑制，会持续膨胀 | 规则编进语义，"写不出来"而不是"写出来会警告" |
| 现有语言 + 强类型框架 | Rust + tokio、TypeScript + tRPC/Zod | 类型系统很强但概念面巨大（trait / 泛型约束 / 类型体操），AI 的失效从语法层转移到概念层 | 概念面固定且极小，不允许多种写法 |
| 新语言（为人设计） | Zig、Gleam、Mojo、Carbon | 目标仍是程序员的性能/安全/表达力诉求 | 目标函数不同：**以 AI 首次正确率和验证成本为第一优化目标** |
| AI 生成专用受限语言 | Safe Gen（Meta, 2023，学术） | 面向"生成即安全"的窄场景，不服务通用服务端与长期维护 | 面向真实服务端工程：跨平台、可持续维护、可延伸到裸机 |

### 1.4 可证伪的核心主张

本项目的全部投入押在三个可证伪命题上。**任何一条被数据否掉，项目应当停止或转向。**

- **P-A（不重训可用）**：一门语言如果足够小，用固定 token 预算的上下文注入 + 少量合成语料，就能让未经微调的主流模型达到高首次正确率。
- **P-B（结构错误占主导）**：服务端 AI 错误中，有可观测的一半以上是**结构性**的（跨边界、资源生命周期、配置、错误传播、并发结构），因此可以被静态/编译期判定；只有业务语义错误不能被语言消灭。
- **P-C（便宜验证是主因）**：首次通过率的提升主要来自"验证反馈便宜且可定位"，而不是语言本身"更安全"。——这条必须有对照组（§11.4），否则 P-B 的成绩无法归因。

## 2. 设计公理与硬约束

### 2.1 四条公理

**公理 1：让"读签名就能推出影响范围"成为唯一规则。**
服务端代码最危险的不可见性不是逻辑复杂，而是"这段代码会跨出哪些边界、会碰什么外部系统、能不能重试"。这些必须在函数签名里，而不是在函数体、配置或框架注解里。

**公理 2：错误必须暴露，且暴露在最便宜的位置。**
静默降级是本语言的头号敌人。任何"两种语义同时生效，必有一种是错的"的情况一律编译失败，不做自动择一、不做静默丢弃、不引入运行时告警代替编译错误。

**公理 3：每个概念只有一种写法。**
选择本身就是错误源。存在两种等价写法（`for` vs `each`、`null` vs `Option`、`panic` vs `Result`）时，AI 必须靠回忆惯例来选择，回忆是概率性的。默认动作是**删掉一个**，不是加一条 lint。

**公理 4：教学面有固定预算，超预算删特性。**
这是硬约束，见 §2.2。它同时是对抗"语言随时间膨胀"的唯一机制。

### 2.2 五条硬约束（可度量，全部纳入 CI 门禁）

| # | 约束 | 阈值（v1 目标） | 违反时怎么办 |
| --- | --- | --- | --- |
| H1 | **教学面 token 预算**：规范 + 全部语言规则 + 核心 API 清单（机器可读形式）的总长度 | ≤ 2000 token | **删特性**，不加文档、不加示例 |
| H2 | **核心关键字数量** | ≤ 14 | 新语法用已有形状表达，或并入类型系统 |
| H3 | **核心原语数量**（内建类型 + 内建函数 + 内建构造） | ≤ 24 | 下沉到包；包不计入教学面，但**必须机器可读**（§7.4） |
| H4 | **常驻内存地板**：空服务（HTTP 健康检查 + 1 条路由 + 日志）的 RSS | ≤ 3 MB | 删运行时机制（反射表、异常表、任务调度器预分配、GC 元数据） |
| H5 | **CPU 地板**：单核、keep-alive 下的空转占用；以及每请求固定开销 | 空转 ≤ 0.5% 单核；每请求 ≤ 2 µs | 取消常驻线程/定时器/心跳；改为按需与静态派发 |

> **H1 是本项目最重要的单一纪律。** 它是"不依赖重训"这一前提的可证伪形式：如果一门语言教不会模型，那它就是太大的语言，无论多有道理都要砍。膨胀的方向有两个，都算违反：加语法糖，和加"好心"的便利 API。
>
> **H4/H5 不是性能偏好，是产品边界。** 服务端语言的现实下限是"能不能跑在 1 核 512 MB、甚至更小的实例上"——这决定了它能不能进生产、能不能进边缘与低成本部署。**"运行时便宜"与"语义可见"在本项目里是同一件事的两面**：反射表、异常表、GC 元数据、全局任务注册表、预分配对象池，这些既是隐形资源消耗，也正是 AI 在源码里看不见、因而无法验证的东西。省下来的每一 MB，都对应少一处不可见机制。详见 §9。
>
> **H1–H3 与 H4/H5 会互相施压，这是有意为之**：前者限制"你要教模型多少"，后者限制"你要在运行时藏多少"。两条约束一起把语言夹在中间。

### 2.3 特性准入判据（替代"我觉得有用"）

任何候选特性必须至少满足一条，否则不进语言：

1. **删掉一个自由度**（消灭一种"两种写法"的情况）；
2. **把一类运行时错误提升到编译期**（且该错误类在 §3 的痛点清单中被列为高频）；
3. **让某类错误从"不可定位"变成"带位置与改法"**；
4. **替换掉一个外部概念**（净减少模型需要学习的东西）；
5. **降低或至少不提高常驻资源**（内存/CPU 地板，§9；H4/H5）。

明确**不**构成理由的：性能优化、表达力、写起来更短、社区要求、"其他语言也有"。

## 3. 现有服务端语言在 AI 时代的痛点

格式：**语言强项 → AI 高频痛点 → 我们要规避什么 / 借鉴什么**。本节清单来自公开讨论与工程常识中的高频问题类别，属于**待验证的工作假设**：S0/S1 阶段要用 §11 的失效面地图逐条核实并量化（哪些真在 AI 生成中出现、频率多高、能否被静态判定）。未被数据证实的痛点不得作为立项理由。

### 3.1 Go

**强项**：编译快（反馈循环便宜）、`gofmt` 唯一写法、工具链一体化、部署即单文件二进制、并发原语简单、错误是值。

**AI 高频痛点**

| 痛点 | 说明 | 类别 |
| --- | --- | --- |
| `err` 可以不被使用 | 声明了错误却写 `_` 丢弃，编译器不拦，成为生产事故的主要来源之一 | C1 静默 |
| `interface{}` / `any` 是黑洞 | 参数写成 `any` 后编译期完全失能；map/slice 元素类型也不检查 | C2 不可判定 |
| **标签式配置**（`json:` / `validate:` / `orm:`） | 结构体的真实契约藏在字符串标签里：字符串可拼错、可与实际字段脱钩，编译器与静态分析都看不见。**这是"行为在字符串里"的最典型形态**，AI 极高频错处（标签名拼错导致静默丢字段） | C1 + C2 |
| 零值即合法 | `time.Time{}`、`int(0)`、空 struct 都是有效值；要表达"未设置"只能用指针，于是把空指针问题请回来 | C2 |
| nil map 写操作 panic、读操作静默 | 同一种值有两种不一致行为，AI 靠记忆而非推理 | C1 |
| goroutine 泄漏 | `go f()` 后无人取消、channel 无人接收即永久阻塞。语言不提供"这个任务的取消归属谁"的可见性 | C3 隐性 |
| `context.Context` 靠仪式 | 首参约定、必须逐层传递、值用 `any` 存取；漏传或新建 ctx 都合法，只在运行时或 code review 暴露 | C3 + C5 |
| 语言版本行为变更 | 例如 `for` 循环变量作用域语义在 1.22 改变，闭包捕获行为随之变化。**训练语料同时含新旧两种语义，模型无法从上下文判断目标版本** | C6 先验污染 |
| 无 sum type → 无穷尽检查 | 枚举加一个值，所有 `switch` 不会报错；`_ default` 让漏分支永久合法 | C2 |
| 整数类型选择成为噪声 | `int` / `int64` / `uint32` 之间的转换必须显式，AI 大量时间花在选类型而不是写逻辑 | C4 表面噪声 |

**规避**：错误不可丢弃（必须传播、转换或显式声明忽略）；不用字符串承载结构；不用"仪式参数"传递横切关注点；不把版本行为差异留给运行时。
**借鉴**：编译速度与工具链一体化是刚需（见 H 约束之外的一条软约束：`check` 必须亚秒级，见 §7.1）；"一个二进制部署"必须作为默认产物；`gofmt` 证明"消灭风格讨论"对机器同样有效。

### 3.2 Python

**强项**：可读性高（AI 的先验最强）、原型速度、生态无可替代、动态性适合胶水。

**AI 高频痛点**

| 痛点 | 说明 | 类别 |
| --- | --- | --- |
| 类型注解只是文档 | 解释器不执行注解；AI 常写完注解就以为"已经校验了"，实际边界上是裸 dict。类型与运行时校验是两套东西，必须手写并保持一致（Pydantic 缓解，但仍是库约定） | C2 |
| `None` 与运行时 AttributeError | 空值错误在运行时才暴露，是本语言要避免的最典型"贵错误" | C1 |
| 可变默认参数 | `def f(x=[])` 的默认值在多次调用间共享 —— 这是"跨请求状态泄漏"的语言级微缩版，AI 高频复现 | C3 |
| 模块级可变状态 | import 即执行，模块作用域在进程内共享；全局 config/cache/client 直接导致并发请求互相污染 | C3 |
| `**kwargs` / 鸭子类型 | 签名不表示实际行为；调用点看不出这个函数会做什么 | C2 |
| **异步着色 + 事件循环阻塞** | 在 `async def` 里调用阻塞库不会报错，只会静默摧毁吞吐；语言无法区分"纯 CPU"与"会阻塞循环" | C1 + C3 |
| 并发范式三选一 | `asyncio` / `threading` / `multiprocessing` 语义与适用场景完全不同，选错无编译期信号 | C3 + C5 |
| 缩进即语法 + Unicode | tokenizer 层噪声：错位不报错、同形异码字符可被构造（历史上有过公开的安全事件讨论） | C4 |
| **环境与依赖不可复现** | pip / venv / poetry / uv / conda 混用，requirements 与 lock 不一致。AI 产出的"能跑的代码"经常不等于"能跑起来的环境" | C5 |

**规避**：类型在边界上强制执行（不是注解而是运行时契约）；没有模块级可变状态；异步与阻塞在类型上可区分；环境正确性属于语言/工具链职责（§8.3）。
**借鉴**：**FastAPI + Pydantic 是"边界即 schema"这一模式的正确性已被工业验证的实例** —— 本语言要做的是把它从库提升为语言构造，从而消掉"忘了写 validator"这一整类错误。同时借它的可读性优先级：语法形状应向 Python/Go 靠近，而不是向 ML/Haskell 靠近（理由与代价见 §5.1、§8.4）。

### 3.3 TypeScript（作为服务端语言）

**强项**：结构类型系统、类型推导优秀、生态即 Web 生态、`strict` 模式逐年变强。

**AI 高频痛点**

| 痛点 | 说明 | 类别 |
| --- | --- | --- |
| 类型可被逃逸 | `any`、`as`、`!`、`@ts-ignore`、`@ts-expect-error` —— **五种**官方逃逸口，AI 在卡住时会全部用上，因为它们都"能过编译"。类型系统的安全前提是"没人逃逸"，而这个前提无法维持 | C1 + C2 |
| 编译期类型运行时消失 | 校验必须手写第二遍（zod/joi/class-validator），于是出现"类型说 A、运行时是 B"的漂移 | C2 |
| 结构性类型 + 宽对象 | 只要字段是超集就能匹配，多余字段静默接受 → 拼错的属性名可能悄悄通过；反过来函数重载与条件类型让"是否匹配"在**读代码时无法判定**，必须交给编译器跑一遍 | C2 + C4 |
| 类型体操不可审计 | 深层 `infer` / 条件类型 / 映射类型的错误信息跨越几十个实例；一个错误的根因报在 200 行外 | C4 + C6 |
| `Promise` 未处理 rejection | 悬空 Promise 只在进程级炸（甚至不炸），没有"必须 await 或显式托管"的约束 | C1 |
| **tsconfig + 包管理器 + Node 版本矩阵** | 语言层与工具层双重不确定性，跨项目不一致；AI 换项目就要重新猜约定 | C5 + C6 |
| 运行时只有一个线程 + 事件循环 | 并发不是语言问题而是部署问题，但"不能阻塞循环"这条铁律在类型上完全不可见 | C3 |

**规避**：**语言内不允许任何形式的类型逃逸口**（无 `any`、无 `as`、无 `!`）——需要不透明数据就用显式的不透明类型，需要失败就失败。逃逸口是"规则太多所以给人逃生"的信号，说明规则本身该重做。
**借鉴**：结构类型 + 推导带来的书写成本低，值得保留"少写类型注解"的体验（但要保证"不写注解 ≠ 不检查"）；`tsc --noEmit` 作为独立廉价闸门的产品形态正确。

### 3.4 Java

**强项**：类型系统成熟、模式匹配与 record 近年显著改善、虚拟线程（Loom）降低并发心智、JVM 性能可预测、生态完整度第一。

**AI 高频痛点**

| 痛点 | 说明 | 类别 |
| --- | --- | --- |
| `null` 与"只警告不阻断"的空值注解 | `Optional` 与 `null` 并存，两套写法；JSpecify 一类注解主要产出警告而非错误，存量代码不受约束 | C1 |
| 受检异常的仪式性包装 | `catch (Exception e) { throw new RuntimeException(e); }` —— AI 大量生成这种把信息毁掉的代码，只为通过编译 | C1 + C4 |
| **注解驱动的行为注入** | `@Transactional` / `@Autowired` / `@Async`：真实行为由运行期代理与容器决定，**从调用点看不见，且同类自调用会让注解静默失效**（经典陷阱）。这是"读代码推不出行为"的最严重形态，对 AI 是纯负资产 | C3 |
| 抽象层数深 | 接口 → 抽象类 → 工厂 → 注册表 → 容器；"该在哪层加代码"需要架构知识，不是局部可判定的 | C3 + C5 |
| DI 容器是隐式全局注册表 | 漏绑定、多绑定、循环依赖都在启动或运行时才暴露；AI 写完代码通常不会去跑容器 | C5 |
| 样板代码 | 一个 DTO 牵扯 builder / lombok / getter-setter / mapper；lombok 又引入"生成的代码看不见"的新不可判定源 | C4 + C2 |
| Maven/Gradle 依赖树 | 版本冲突与传递依赖只在运行时爆 `NoSuchMethodError`；AI 无法廉价验证 | C5 |

**规避**：不用注解承载行为（行为必须在签名上可见）；不用 DI 容器作为语言机制的替代（能力显式注入，见 §5.4）；不用生成代码补足语言空缺。
**借鉴**：JVM 三十年积累的**性能可预测性与观测性**是服务端硬指标，我们的运行时/规范必须给 profiler 留出稳定语义（栈可归因、任务可命名）；**Loom 的方向正确**——并发单元应当轻量且默认有明确归属，这正是结构化并发（§5.5）。穷尽 `switch`（Java 17+）也证明"加一个枚举值就报错"是能被主流语言吸收的正确设计。

### 3.5 C#

**强项**：语言层打磨质量最高之一、LINQ 表达力强、`async/await` 的普及形态、nullable reference types、Blazor/.NET 运行时工程质量高。

**AI 高频痛点**

| 痛点 | 说明 | 类别 |
| --- | --- | --- |
| 多种等价范式并存 | `foreach` / LINQ / `Parallel` / `async` / TPL Dataflow / `Channel`：同一件事有五六种正确写法，**选错不会失败，只会变慢或引入竞态** | C3 + C5 |
| 可空注解是渐进式 | NRT 主要产出警告，存量代码大量 `null!` 抑制；`string?` 到 `string` 之间仍有 unchecked 路径 | C1 |
| `async void` | 异常无法被 await 捕获，直接冒到同步上下文；合法但危险 | C1 |
| 框架魔法密集 | middleware 管道、filter、model binding、host builder、源生成器 —— 行为分散在注册顺序与生成代码里，跨文件不可见 | C3 + C5 |
| 版本特性矩阵 | `partial` 类、源生成器、`record`、`required`、顶级语句跨版本组合多，AI 需知道目标 TFM 才能选对写法 | C6 |
| 运行时/部署形态多 | self-contained / framework-dependent / AOT / ReadyToRun 的选择影响极大，且不写清就没有信号 | C5 |

**规避**：**宁可表达力弱，也不留多种等价写法**（公理 3 的严格应用）；不引入源生成器补足语言空缺。
**借鉴**：`async/await` 的形状与 `Task<T>` 的返回类型约定应该保留——它已经是跨语言的最大公约数，模型先验极强；LINQ 的"链式数据变换"体验好，但要用**一种**形式提供（管道函数或推导式，二选一）。

### 3.6 Rust（关键样本：它验证了假设，也暴露了天花板）

Rust 必须单独讨论，因为它是"**语言层安全能否让 AI 少犯错**"这个命题最接近的天然实验。

**它证明了什么**：`Result`/`Option` + `?` 让错误传播成为签名的一部分，穷尽 `match` 让新增枚举变体强制暴露所有使用点，所有权让一批内存错误变成编译错误。**这些机制的意图与本语言高度一致**，是首要借鉴对象（§5.2、§5.6）。

**它同时暴露的天花板**

| 现象 | 对 AI 的实际后果 | 类别 |
| --- | --- | --- |
| **编译错成串** | 一个所有权误用触发几十个连带错误，第一个报错位置常不是根因。代理陷入"修一个报错又冒出三个"的循环，把改动当成随机噪声处理，最终生成大量"为了让编译器闭嘴"的代码 | C4 + C6 |
| **`unsafe` 是最便宜的通关方式** | 卡住时模型倾向于加 `unsafe`、`.unwrap()`、`.clone()`、`#[allow(...)]` —— 全部合法、全部静默降级、全部把错误推回运行时。任何"允许逃生"的机制，在优化通关的代理面前都会被系统性滥用 | **C1（本项目最重要教训）** |
| 异步 trait 对象与 `Send`/`Sync` 边界错误 | 错误信息跨越大量泛型实例，根因在调用图另一端；模型很难定位 | C4 |
| trait bound 求解不可见 | "为什么这个类型不满足 trait"在源码里没有答案，需要理解 impl 图的全球结构 | C2 + C3 |
| 借用检查器需要全球推理 | 与公理 1（本地可推）方向相反；生命周期参数是纯概念负担 | C2 |
| 编译时间长 | **反馈周期长 → 代理倾向少验证甚至不验证 → 语言再安全，错误也从"未验证"这一侧漏进来** | C5 |
| 生态 API 面巨大 | "用哪个 crate"的选择错误是主要风险，与语言安全性无关 | C5 |

**规避**：
1. **错误必须是局部、单点、可解释的。** 设计目标之一是"一个误用只报一个错，且报在真实根因位置"。这直接约束类型系统：宁可弱一点，也不要产生级联错误（这一条比"更强的静态保证"优先级高）。
2. **不提供 `unsafe`。** 需要绕过正确性约束的场景，一律通过显式的外部能力（`host` 块）完成，它在产物里可 grep、可统计、可审计。逃生口必须是"跨边界"而不是"关检查"。
3. **不做需要全球推理的静态检查。** 生命周期、隐式 trait 求解、跨模块的类型推断循环 → 都不做。可判定性优先于精确性。
4. **亚秒级检查是语言承诺，不是实现细节。** 增量检查器进第一阶段，与编译器同优先级。

**借鉴**：`Result` + `?` 的错误传播形状；穷尽 `match`；`Drop` 语义的正确性诉求（用所有权与区域实现，而不是用隐式钩子）；`cargo` 的 lockfile/可复现构建思路。

### 3.7 其他有参考价值的样本

- **Zig**：**"分配器必须是显式参数"** 是服务端与嵌入式共同的正确答案之一，直接对齐 C3（模块级/隐式全局状态）与 §10（静态内存上界）。同时它是"新语言靠自托管 + C ABI 成活"的高门槛样本，不作路径照抄。
- **Gleam**：一门小语言通过**编译到既有 VM**（BEAM/Node）绕过生态冷启动，且语法刻意保持浅学习曲线 —— 这是 §8 跨平台策略的直接先例。
- **Mojo**："为 AI 基础设施设计新语言"的先例，说明这个赛道存在；其动机主要是性能与 Python 生态断层，而不是"减少 AI 生成错误"，与本项目目标函数不同，仅作存在性参考。

## 4. 七类失效聚类（设计约束）

§3 的痛点收敛为七类（C1–C6 是正确性失效，C7 是资源失效，它同样致命但常被归到"性能优化"而被忽略）。后续每个语言特性都必须挂到某一条上，否则不予立项（对应 §2.3 判据）。

| 聚类 | 名称 | 定义 | 典型来源 | 语言层应对 |
| --- | --- | --- | --- | --- |
| **C1** | 静默失败 | 错误代码合法通过所有检查，且没有任何信号 | Go 丢弃 err、TS 逃逸口、Rust `unwrap`、Py 悬空默认参数、C# `async void` | 禁止丢弃、禁止逃逸口、错误必传播（§5.6） |
| **C2** | 不可判定契约 | 正确性所需事实在类型系统之外（字符串、反射、生成代码、隐式注册） | Go struct tag、Jackson、DI 容器、源生成器、Py 注解 | 契约必须在签名上；边界 schema 是一等类型（§5.3） |
| **C3** | 隐性状态与耦合 | 行为依赖本地读不到的全局/环境/顺序 | 模块级可变状态、`@Transactional`、事件循环、框架中间件顺序 | 无全局可变状态、效果进签名、能力显式注入（§5.4） |
| **C4** | 概念与表面噪声 | 认知预算花在选写法/选类型/读天书报错，而不是表达意图 | Java 样板、TS 类型体操、Rust 级联错误、C# 多范式、Go 整数类型 | 每事一写法（公理 3）；数值类型收敛；错误单点可解释 |
| **C5** | 环境正确性 | 代码正确但构建/运行不起来；依赖、配置、部署漂移 | pip/venv、Maven 依赖树、Node 版本矩阵、.NET 部署形态 | 工具链承担：hermetic 构建 + 类型化配置（§5.7、§8.3） |
| **C6** | 先验污染 | 模型带着旧语义/旧惯用法生成新代码；语言自身变过 | Go 循环变量语义、Py2/3 残留、TS 配置漂移、Java 版本特性矩阵 | **新语言的最大结构性红利**：无存量、无历史包袱、语义一次定终身（§4.1） |
| **C7** | 资源无界 | 内存/CPU 用量由运行时机制与库自行决定，源码里看不出上界；无界缓存与无界查询导致 OOM 与成本失控 | JVM/CPython/Node 的常驻固定税、Go 无界 goroutine、各语言的无界 map 缓存、APM/指标的高基数 | 无 GC 无反射无全局注册表（§9.3）；`cap` 进签名成为类型事实（§9.5）；静态链接单文件产物 |

### 4.1 C6 值得单独强调

C6 是**存量语言无法修复、而新语言免费获得**的优势。Go/TS/Java/Python 的每一个"版本行为变更"都会永久污染模型先验：训练语料里同时存在两种语义，而模型无法从上下文推断目标版本。这类错误不是"模型不够好"，是**语言的历史**造成的，无论怎么训练都消不掉。

对本项目的含义：**这条是新语言立项理由中最硬的一条**，也是 P-A 主张的主要支撑。它同时给出纪律——**droplet 发布后不得做任何行为不兼容的语义变更**（新语法糖可以有，已有语义不可以改），否则我们把自己变成下一个 C6。这条应写进语言章程。

## 5. 语言核心设计

详细原语清单与语法示意见 §14。本节只写"设计意图 + 对应聚类"。

### 5.1 语法形状（→ C4、C6）

- 形状向 **Go/Python 家族**靠拢，不向 ML/Haskell 靠拢。理由：服务端领域先验最强的语法能显著降低语法层错误，而我们已经不需要靠语法独特性表达任何东西。
- 有括号与显式块，**不以缩进承载语法**（消除 tokenizer 层风险与错位静默）。
- 无运算符重载、无隐式转换、无重载函数、无隐式变量提升。优先级表压到 ≤ 5 级，允许并要求显式括号。
- 无 `class`、无继承、无 mixin、无装饰器、无元编程（不提供"框架自造 DSL"的能力 —— 这是 C3 的源头，见 §6）。

### 5.2 数据与计算（→ C1、C2、C4）

- 值类型默认不可变；命名记录（record）+ 带载荷的判别联合（sum type），`match` **必须穷尽**，无 `default` 逃逸。
- **没有 null**。可选性由联合类型表达；缺省值必须显式构造，零值不合法（吸取 Go 零值教训）。
- 数值类型收敛到极少几种：固定宽度整数（`i64`/`u64` 等）+ 精确十进制（金额）+ 浮点（必须显式标注"这是近似值"）。**默认整数是一种**，避免 Go 式"选类型"噪声（→ C4）。
- 函数是一等值，无方法语法糖带来的两套写法；副作用必须出现在效果集里（§5.4）。
- **字符串是字节序列 + 显式编码**，索引/切片按码元的行为必须明确定义（跨语言历史 bug 高发区）。

### 5.3 边界（boundary）—— 本语言最重要的服务端构造（→ C2、C3）

对应现实里的 RPC / HTTP / 消息 / 队列 / 进程间数据交换。设计原则：**跨边界的数据是显式声明的、可序列化的、有版本的事实，而不是"编译器恰好没检查的内存布局"。**

```
boundary UserApi @v1 {
  get(id: Id<User>): User
  update(id: Id<User>, patch: Patch<User>): User with idempotency
}
```

一条声明同时产出：调用桩、服务端入口、序列化代码、schema 文档、机器可读契约、幂等性要求。

- **只有声明过的类型可以跨边界**（结构/联合/基本类型；不透明句柄、函数、区域引用一律编译失败）。
- **函数不能跨边界**（无回调式 API，消除一整类"传了个东西过去，另一端收到 null/undefined"的错误）。
- `with idempotency` 是强制标注项：重试语义必须写在边界声明上，因为重试的正确性不可在调用点局部判定（§3.1/§3.5 的并发范式选择问题）。
- 版本演进规则内置：字段只能增/标可选/标废弃，破坏性变更必须升 `@v`；违反即编译错误。

### 5.4 效果与能力（effects & capabilities）（→ C2、C3）

**目的**：让"这段代码会跨出哪些边界、代价是什么"在签名上可见（公理 1）。

- 每个函数有效果集：`{}` 纯；`{db:users_read, http:*.stripe.com, clock}` 等。
- 效果通过**能力值（capability）**持有，不存在环境权限（无全局 `fetch`、无全局 `Math.random`、无 `process.env`）。这是"读代码推不出行为"问题的根治：能碰什么 = 手上有什么能力 = 参数列表。
- 效果多态用集合变量表达，**不引入函数着色**（`async` 污染整张调用图是 C3/C4 的重大来源）：纯函数可在任何位置使用，需要 `{}` 的地方可以接受 `{db}` 的调用被显式标注，反之不行。
- 每个效果都有可检查属性：是否只读、是否可重试、是否可并发、成本上界（用于 §7 的验证与 §11 的性质合成）。
- **`host` 块**：唯一能突破语言规则的位置，用于绑定既有 C 库 / 平台能力。它是"跨边界"，不是"关检查"——在产物中可 grep、可统计、必须显式声明效果，且不继承语言的安全承诺。这是从 Rust `unsafe` 教训（§3.6）直接导出的设计。

### 5.5 并发（→ C3、C5）

- **只有结构化并发一种**。任务必须有 owner；函数返回时，它派生的所有任务必须已完成或已被显式移交；取消自上而下传播，带超时预算。
- 任务不"脱管"（消除 Go `go f()`、C# `async void`、TS 悬空 Promise 这一整类）。
- 通信走有界 channel，满/空策略在类型上可选，**没有"无人接收即永久阻塞"这个默认行为**。
- 阻塞与异步在效果系统上可区分（消除 Python 事件循环静默阻塞）。
- 内存共享用消息 + 区域转移（§5.8），**不提供跨请求共享可变状态**。这条直接封堵 Java/Spring 与 Python 都踩过的"跨请求状态泄漏/串号"，也是服务端最贵的一类事故。

### 5.6 错误处理（→ C1）

- 错误是值，失败类型写在签名里：`fn get(id: Id<User>): User | NotFound | DbError`。
- **错误值不可丢弃**：不处理就编译失败。三种合法出路必须显式：`!` 向上传播、`match` 处理完、`ignore(reason: "...")` 显式声明忽略并留痕（可 grep、可统计，进入 §11 的度量）。
- 无 `panic`、无 `recover`、无异常穿透中间件。进程级不可恢复故障只有一个机制：**fail-stop** —— 让入口层决定如何降级，绝不在业务函数内部恢复。
- `!` 是语法糖不是新概念（吸取 Go 每处手写 `if err != nil` 的表面噪声教训，也吸取 Rust `?` 的成功）。

### 5.7 配置、密钥、环境（→ C5、C1）

**本语言差异化的第二个重点。** 上文各语言对"配置"的处理几乎全是最弱的形态：字符串 map + "记得检查"。而服务端最贵的生产事故恰恰集中在配置与环境。

- 配置在编译期按环境实例化：`env` 声明一次，**每个环境必须补齐所有键**，缺键即编译失败 —— 把"部署时才炸"提到构建阶段。
- 密钥是不透明类型：不可读、不可打印、不可进日志格式化，只能透传给声明接受它的效果（消除密钥泄漏到日志这一整类事故）。
- feature flag 有类型与生命周期（含"到期未删则构建警告"），因为它天然会被遗忘。
- 配置不是 map、不是字符串、不是环境变量名 —— 它是类型。任何 `config.get("...")` 形式的 API 都不存在。

### 5.8 内存模型（→ C1、C3、§10 裸机）

**选型：仿射类型（可丢弃的线性类型）+ 显式区域（region/arena），无 GC，无借用检查器。**

这是全文最关键的一个技术决策，理由与代价如下。

**为什么不选别的**

| 方案 | 否决理由 |
| --- | --- |
| GC | 与裸机/实时约束冲突（§10），且常驻 10–50 MB 的运行时直接顶穿 H4 内存地板（§9）；还给"资源生命周期"留下不确定性——连接、句柄、事务仍需显式关闭，GC 只解决内存 |
| refcount | 循环 + 隐式行为不可见；对 AI 不友好（看不出错在哪） |
| Rust 式借用检查 | **需要全球推理，直接违反公理 1 与 §3.6 教训**；错误级联，且生命周期参数是纯概念负担（H1 预算承受不起） |

**为什么仿射 + 区域能同时服务服务端与硬件**

- 服务端：连接、事务、文件句柄、游标、订阅、锁都是"必须释放的资源"。用线性/仿射类型后，"忘了关闭事务"和"事务跨越了网络调用"从 code review 问题变成**编译错误**（→ C1 + C3）。
- 硬件：无 GC、静态分配、每区域内存上界可在编译期算出 —— 这是嵌入式立项的前置条件（§10）。
- 与 AI 的适配性最好的一点：每个检查都**局部可判定**（"这条路径上这个值有没有被消费两次/丢弃"是流敏感的局部性质），因此错误能报在真实位置且**单点**，不产生级联。
- 仿射（可丢弃）而非严格线性：允许"不用"，因为服务端大量句柄确实需要依赖作用域自动释放；但**丢弃即释放**，语义唯一。

**代价（必须写进文档，不藏）**

1. 效果集与区域会进入函数签名，签名变长 → 靠类型推导 + 短效果名缓解，并允许效果集省略为 `{}` 才需要标注（纯函数标注是提示"这是纯的"，而非负担）。
2. 条件分支/提前 return 会让"消费未定义"，这是最常见的误报源 → 必须提供机械的自动资源作用域（`with` 形式）覆盖 90% 场景，手写所有权只在少数地方出现。
3. 图结构/循环引用仍需专门原语 → 提供 `cell`（受区域所有、可更新的单值格），不引入垃圾回收。
4. **认知成本对人是真实的。** 我们接受它，换来的是 AI 的失效面显著缩小；而人是维护者（读得多、写得少），可读性靠"写法唯一 + 签名自解释"来保障，不靠"没有概念"来保障。

## 6. 反模式清单（我们主动排除的东西）

这份清单是语言的一部分。每条都对应 §3 中至少一个痛点。

| 排除项 | 为什么 | 来源 |
| --- | --- | --- |
| 类型逃逸口（`any` / `as` / `!` / `@ts-ignore` / `#[allow]` / `unsafe`） | 优化通关的代理会系统性使用它们，把错误推回运行时 | TS、Rust |
| 注解/装饰器承载行为 | 行为从调用点消失，且同类自调用会静默失效 | Java、C# |
| 字符串/反射承载结构（struct tag、ORM 映射、JSON path） | 契约不可静态判定、拼错静默失败 | Go、Java |
| 模块级可变状态；import 即执行副作用 | 跨请求污染 | Python、JS |
| 环境权限（全局 `fetch` / `process.env` / 系统时间 / 全局随机） | 效果不可见；不可确定性重放 | 全部 |
| 多种等价写法（两种循环、两种并发、两种可空） | 每个选择都是一个错误源 | C#、Java、Py |
| 继承 / mixin / 元编程 / 操作符重载 / 函数重载 | 行为不可本地判定；跨文件全球推理 | Java、C# |
| 未处理错误可编译通过 | C1 的头号实例 | Go、TS、C# |
| 隐式转换与零值合法 | 静默的语义降级 | Go、Java |
| 生成代码补足语言空缺 | 不可 grep、不可审、报错位置错位 | Java lombok、C# 源生成器 |
| 语言语义的不兼容变更（发布后） | 自我制造 C6 先验污染 | Go、Py2/3、TS |
| 运行时反射与运行时类型元数据 | 吃内存、藏契约；AI 看不见即无法验证 | Java、Go、Python |
| 异常展开表与 landing pads | 二进制体积 + 冷路径开销 + 静默穿透中间件 | Java、C#、C++ |
| 常驻后台线程 / GC / 心跳 / 预分配 worker 池 | 空闲就吃 CPU 与内存，最小实例上先占掉一半余量 | JVM、Go、Node、tokio 类 |
| 无界缓存与无界查询（默认 map、默认 `SELECT *`） | OOM 与成本失控的头号来源，且源码里看上界不出来 | 全部 |
| 自适应池 / 自动批处理 / 动态预取等"运行时自己扩缩" | 内存不回落、行为不可预测，且不可静态验证 | JVM GC、连接池库 |

## 7. 错误系统与可验证性

**这是"AI 自我找出并修复"的技术承载体。** 前面各节让错误难以写出，本节让已写出的错误**便宜地暴露、精确地定位、机械地修复**。

### 7.1 `check`：一等命令，亚秒级

- 独立于构建、独立于后端、可增量、输出机器可读。AI 的默认动作应是"写完就 check"，所以它必须比思考更便宜。
- 这是语言承诺（对应 §3.6 的 Rust 编译时长教训）：**反馈慢的语言，代理会减少验证**，于是语言安全性被"未验证"抵消。

### 7.2 错误码：稳定、分域、带改法

`AXExxxx`，`error.code/file/line/column/hint/relation` 全字段可 JSON 序列化。

| 域 | 含义 |
| --- | --- |
| E0 | 语法与解析 |
| E1 | 类型与匹配（含穷尽性） |
| E2 | 效果与能力（权限缺失、只读违规、可重试性不匹配） |
| E3 | 边界与序列化（跨边界类型、版本演进、幂等） |
| E4 | 生命周期与所有权（未释放、二次使用、跨作用域） |
| E5 | 并发结构（脱管任务、channel 策略、取消传播） |
| E6 | 配置与环境（缺键、密钥误用、flag 生命周期） |
| E7 | 数据访问（查询与 schema 不符、N+1、事务跨越） |
| E8 | 资源预算（`cap` 上界被违反、无界缓存/查询、栈深超限、指标基数超限，§9.5） |

**每条错误的硬要求**：报在真实根因位置；不产生级联（同一根因只报一次，其余标为 `caused_by`）；`hint` 必须是可执行的改写建议，而不是复述规则。

### 7.3 修复分级（关键纪律）

| 级别 | 行为 | 适用 |
| --- | --- | --- |
| **L1 auto-fix** | 直接改，无需理解意图 | 纯语法/形式修正：补 `!`、补穷尽分支的**占位并标记 TODO**、显式化隐式转换 |
| **L2 suggest** | 输出 diff 建议，不自动落地 | 语义可能改变的两条路：区域归属、错误合并策略、重试语义 |
| **L3 explain** | 只解释"为什么会错、正确的形状是什么" | 概念性错误（共享可变状态、跨边界传函数） |

**纪律**：**能通过"猜测意图"来自动修的，一律不许自动修。** 理由：自动修会让代理"通过但没学会"，同时引入静默的语义降级 —— 这与公理 2 冲突。这条是我们在设计阶段就必须定下的反退化机制（对抗"每发现一个 AI 错误就加一条自动修"的自然倾向）。

### 7.4 契约可导出（解决"API 面大"与"教学面预算"的冲突）

H1 要求教学面 ≤ 2000 token，但服务端语言必然要连 Postgres/HTTP/MQ。解法：**教学面小 ≠ API 面小，前提是 API 必须机器可读。**

`droplet contract` 导出包/项目的完整契约 JSON（类型、函数、效果、边界、资源所有权、幂等性）。代理读契约而不是读源码。

**这条准入条件应写进规范：任何进入核心语言之外的 API，必须能仅凭契约被正确使用（不看实现）。做不到就说明该 API 的形状本身有问题。**

### 7.5 验证器分层（成本递增，代理按序消费）

1. 类型 / 效果 / 边界 / 资源检查（毫秒级）
2. 性质检验（秒级）：从声明自动合成，见 §7.6
3. 符号/约束检查（十秒级）：schema ↔ 查询、状态机可达、重试幂等
4. 动态：确定性重放测试、集成测试（分钟级）

### 7.6 从声明合成 oracle —— 填掉"没人写断言"的缺口

服务端有一批**天然成立的不变量**，可由语言里已有的声明直接生成，不需要人工写断言：

- 往返：`.set(x)` 之后 `.get()` 必须为 `x`（来自区域/cell 声明）
- schema 一致：响应必须匹配 `boundary` 声明（来自边界声明）
- 幂等：同 `idempotency_key` 重复调用，副作用只发生一次（来自 `with idempotency`）
- 只读不变：标记只读的效果执行前后数据不变（来自效果属性）
- 环境全覆盖：每个环境都能成功构造配置（来自 `env`）
- 密钥不外泄：任何日志/错误消息中不出现 opaque 值（能力不可能构造，故该性质天然成立，测试用于防回归）

这组机制是"AI 自纠"能落地的真正前提：**oracle 必须是声明的副产品，而不是人写的测试**。语言设计的深度决定可合成性质的数量。

### 7.7 确定性重放（一等公民）

无环境时间/随机/全局 → 一次执行可由 `(seed, 时钟输入, 外部响应记录)` 完整重放。`droplet trace` 产出可回放的执行记录，代理能"看到"错误发生的路径，而不是只看日志尾部。

## 8. 跨平台与编译策略

### 8.1 结构

```
droplet 源码 → [类型/效果/资源检查] → droplet IR → 后端
                                          ├─ 后端 1：原生 C 代码输出（v1 唯一后端）
                                          ├─ 后端 2：WASM / WASI（沙箱与浏览器/边缘）
                                          └─ 后端 3：MCU（依赖 C 后端 + 平台目标三元组）
```

**v1 只做 C 输出后端**，理由：一次性继承全部平台的编译器工具链与目标架构（与 Solidity/Zig/Emscripten 同一路径），是"跨平台 + 未来裸机"两个目标的最短共同解；且 C 层天然是 `host` 块的对接面。

### 8.2 各平台语义必须一致（否则 C5 换个地方重现）

GC/无 GC、单线程/多线程、有 OS/无 OS 之间的行为差异是分布式系统之外的第二大数据中心。规范必须对以下项给出跨后端一致的定义：整数溢出、字节序、时间/时钟、错误码、资源释放时机、日志格式、**内存与栈上界的计算口径（§9.4）**。**这些一致性要用同一份跨后端符合性测试集钉住**（这是语言资产，不是测试负担）。

### 8.3 工具链承担"环境正确性"（→ C5）

- `droplet.toml`：依赖 + 编译器版本绑定 + 目标三元组 + 环境清单，单一来源；`lock` 文件强制可复现。
- 单一构建命令：`droplet build/check/test/run/replay/contract`，AI 只需记一个动词表（对应公理 3）。
- 版本单一：安装即确定，无"PATH 顺序 / 虚拟环境 / 运行时选择"。这是相对 Python/Node/Java 的结构性优势，必须在第一天就做对，否则一切语言层的严谨都会被环境噪声淹没。

### 8.4 为什么不"编译到 TS 先拿生态"

它确实是最快的生态路径（Gleam 模式）。但对本项目有害：宿主语义会把 §5 的设计全部稀释（借用/仿射语义在无 GC 的 JS 上只能靠约定，效果集在运行时不可见，配置类型化退化成对象）。**妥协一旦发生，我们的 P-A/P-B 实验测的就是宿主的天花板而不是语言的天花板。**
结论：C 后端起步，生态靠 §7.4 的契约机制 + 后期按需求加托管后端桥接（作为包，不作为语言底座）。

## 9. 生产资源预算：内存与 CPU 占用作为硬约束

**这一节的性质与前几节相同：它不是性能优化章节，而是设计约束。** 资源占用决定这门语言能不能进生产、能不能进边缘与低成本部署，因此它和 H1（教学面预算）一样，是**先于实现定下、由 CI 长期守着**的门槛。

### 9.1 部署基线（目标场景，不是理想场景）

| 项 | 约束 |
| --- | --- |
| 最小平可运行实例 | **1 vCPU / 512 MB**（目标），可退化到 1 vCPU / 128 MB（边缘、廉价 VPS、sidecar） |
| 单服务常驻内存（RSS） | 空服务 ≤ **3 MB**（H4）；含 20 条路由 + DB 连接池 + JSON/HTTP 的常见服务 ≤ **16 MB** |
| 空闲态 CPU | keep-alive 下 ≤ **0.5% 单核**（H5），无心跳、无常驻清扫线程 |
| 每请求固定开销 | ≤ **2 µs**（路由派发 + 作用域建立 + 日志写入） |
| 冷启动 | ≤ **15 ms**（影响按量伸缩与 Serverless 场景的可部署性） |
| 产物 | 单一静态二进制，运行期**无解释器、无虚拟机、无 JIT、无守护进程** |

这几条合起来才是"能吃配置越少越好"的可执行含义：**在生产的最小实例上跑得起来、跑得住、跑得起几千个实例而不炸成本。**

### 9.2 资源都花在哪：机制级削减清单

服务端语言运行时的内存与 CPU 消耗，几乎全部来自**机制**而不是**代码**。下表是本语言的削减清单，每一行都同时是一条资源决策和一条"语义可见性"决策。

| 常见消耗源 | 谁在吃 | droplet 的处置 | 代价 |
| --- | --- | --- | --- |
| GC 运行时 | 堆元数据、写屏障、灰名单、调度线程；典型常驻 10–50 MB | **无 GC**（仿射 + 区域，§5.8） | 区域/所有权概念要学 |
| 通用堆分配器 | 元数据每块 16–32 字节；碎片导致 RSS 只涨不回 | **区域线性分配**，作用域结束整块回收 | 跨作用域引用需显式化 |
| 线程栈 | 默认 1 MB/线程 | 结构化并发单元用**有界固定栈**，栈深由 `droplet mem` 静态算出 | 无递归爆栈风险，但深度上限要在 S1 定死 |
| 异步运行时/调度器 | tokio 类：worker 线程 + 任务对象 + 定时器堆，几十 MB 起 | **调度器内建且最小化**，无常驻 worker 池预分配 | 需自证与生态可比 |
| 反射表 | 类型元数据 + 方法表 + 注解存储；Java/Python/Go 结构性开销 | **无运行时反射、无标签、无注解** | 泛型序列化靠代码生成而非运行时自省 |
| 异常表 | .eh_frame / landing pads，占二进制体积，冷路径还慢 | **无异常**，错误是值（§5.6） | 传播靠 `!`，可读性略降 |
| 动态链接运行时 | libc/libstd 多份副本、重定位开销 | **静态链接**，无运行时依赖 | 与"二进制体积"互施压，见 §9.6 |
| 全局注册表 | 指标注册表、路由表、DI 容器、连接池预热 | **无全局可变状态**（§5.4 能力注入的自然结果） | 显式传参略啰嗦 |
| 空闲定时器/心跳 | 健康检查、连接保活、后台清扫 | 一律**按需 + 事件驱动**，禁止常驻周期任务 | 需内建 idle timeout 语义 |
| 序列化运行时 | JSON 反射解码器、proto runtime | **编译期代码生成**，产物只含实际用到的分支 | 编译时间换运行期，符合 H5 |
| 观测层 | APM agent、采样器、分布式追踪 | **零成本默认**：静态 counter + 固定桶直方图，每指标内存上界，超预算 check 失败 | 不提供动态标签（也是防高基数事故） |
| 缓存 | 无界 map + LRU 元数据 = OOM 的头号来源 | `cache` 必须声明容量与淘汰策略；**无界缓存在类型上不可构造** | 每次写缓存要做决策，但消灭整类事故 |

**规律**：这张表里删掉的每一项，都同时满足两个条件——它吃掉内存/CPU，**并且它的行为在源码里不可见**。反射让契约藏在字符串里（C2）、全局状态让污染跨请求（C3）、GC 让释放时机不可知（C1）、异步运行时让阻塞代价静默（C1）。

> **这就是"省资源"和"AI 少犯错"是同一件事的原因**：隐形机制之所以隐形，正因为它在运行时替你做了你看不见的决定；而它替你做的每一个决定，都在内存里占了一块地方。**AI 验证不了的东西，通常也正是最贵的东西。** 这条规律应当被当作本项目的核心设计线索之一来使用：遇到取舍时，"能不能同时省下一处不可见机制和一份内存"是比"哪个方案更优雅"更强的判据。

### 9.3 三条"无"原则（资源与语义的公共下界）

1. **无运行时反射** —— 一切结构在编译期展开；不生成运行时类型元数据。
2. **无异常机制** —— 失败在签名里，不生成异常表与展开帧。
3. **无全局可变注册表** —— 能力、路由、指标、连接池都属于某个显式作用域；没有"注册即生效"。

这三条一次性削掉 GC 之外的主要固定开销，同时封堵 C1/C2/C3。它们不是性能技巧，是语言能力的**边界声明**：任何需要运行时反射才能实现的库，在本语言里必须以编译期代码生成重做，否则不进入生态。

### 9.4 度量与门禁（不可度量就不是约束）

| 命令 | 用途 | 门禁方式 |
| --- | --- | --- |
| `droplet mem` | 输出全局/每区域/每任务的内存上界报告 + 峰值栈深 + `cap` 声明汇总 | 报告进入 PR diff；超预算即失败 |
| `droplet bench --gate` | 标准微基线集（echo / JSON / DB 往返 / 并发派发 / 冷启动） | 基线快照入库，**回归 >5% 失败** |
| `droplet size` | 静态二进制体积 + 各段占比（代码 / 生成序列化 / 静态库） | 预算制（见 §9.6） |
| `droplet RSS` | 真实容器（cgroup limit 设死）下的常驻与增长曲线 | 长稳测试：48 h 内存斜率必须为 0 |

**方法论说明**：以上数字均为**目标值**，不是实测值。它们由 §9.1 的部署基线反推得到，必须在 S1 阶段（检查器原型 + 3–5 个样例服务）用真实实现复核。若某条被证明无法达到，**优先调整语言的机制数量（删一处运行时），而不是放宽阈值**——放宽阈值等于放弃约束。

### 9.5 与 AI 可验证性的合流：`cap` 是类型的一部分

资源上界不只是运维需求，它给 AI 提供了一个**新的可检查维度**：

```
fn list_users(db: db[users:read], cap: mem<16KiB>) -> [Summary] | DbError
// 违反 cap 上界 => E8xxx 检查失败（编译期/静态分析，非运行时告警）
```

- 每个请求的内存预算、每条流的缓冲上限、每个缓存的容量，都是签名上的事实，调用方与检查器都能看见。
- 直接消灭两类最贵的服务端事故：**无界查询**（`SELECT *` 拉全表进内存）与**无界缓存**（"就加个 cache"变成 OOM）。这两类在 Go/Java/Python 里目前只能靠 code review 和事后监控。
- 与 §11.2 的性质合成对接：`cap` 声明本身即是一条可自动验证的不变量。
- 同一机制在裸机上升级成硬要求：**每区域内存上界编译期可算**（§10）。一次设计，服务端与硬件两头收。

### 9.6 代价与冲突（不藏）

1. **静态二进制体积与"特性完整"互相施压。** 静态链接 + 代码生成会把体积推高（HTTP/2、TLS、压缩、序列化各有一份代码）。需要设体积预算并靠"按需生成"守住：未被调用的泛型实例与未使用的协议分支不进产物。
2. **无 GC 与图结构数据。** 循环引用要靠 `cell` + 区域归属表达，写起来比 GC 语言啰嗦。我们接受这个代价，因为 GC 的内存与尾部延迟成本是常驻的，而啰嗦只在少数地方发生。
3. **优化与"错误单点可解释"冲突。** 激进的跨函数优化会让报错位置偏离根因（§13 已把这条列为风险）。裁决：**资源预算是硬约束，但达到预算的方式只能是"减少机制"，不能是"更激进的优化"** —— 后者会牺牲定位性。
4. **有界栈限制了递归深度**，某些算法写法要改成显式栈。这是刻意的（嵌入式前置 + 防栈溢出），并在错误信息里给出改法。
5. **小内存与高吞吐存在张力**：连接池、缓冲区、任务池都是"用内存换吞吐"。本语言的选择是**默认小、显式放大**——所有需要预分配的东西都要写进 `cap`/配置，不允许库私自扩张。

### 9.7 借鉴与规避

- **借鉴 Go**：静态链接单文件产物、按需增长的 goroutine 栈、极简链接期。这是"部署便宜"的工业参照形态。
- **借鉴 Rust**：零成本抽象的方向、`panic=abort`（无展开帧）与 `opt-level` 取舍——证明"无异常"在真实语言里可行。
- **借鉴 Zig**：分配器作为显式参数，同时服务低成本部署与裸机；这是 `cap`/region 设计的直接来源。
- **规避 JVM / CPython / Node 的固定税**：一个空服务常驻几十上百 MB，在 1 核 512 MB 实例上等于**运行时先吃掉一半产品余量**。这不是实现质量问题，是机制设计问题，因此在语言层就排除：不引入需要 JVM/解释器/事件循环宿主才能运行的形态。
- **规避"运行时帮你自动扩缩"的便利**：自适应池、自动批处理、动态预取这类机制在压测里漂亮，在生产里是内存不回落与不可预测的来源，而且**AI 完全无法从源码验证**。一律不做默认，要做就显式声明并计入 `cap`。

## 10. 裸机/嵌入式延伸的预留约束

**不是 v1 功能，是 v1 必须遵守的约束。** 现在不锁死，将来做硬件就要重做语言。

硬件后端的五个前置条件：

1. **静态内存上界可计算**：每个区域的峰值用量编译期可导出（`droplet mem --bound`），这是嵌入式立项的硬需求；→ 因此无 GC、无隐式全局堆（§5.8）。
2. **无运行时分配或分配显式**：吸收 Zig 的"分配器是参数"。
3. **中断/回调语义可表达**：中断是"由硬件触发的效果"，需要进效果系统而不是变成 C 回调；v1 设计效果类型时必须留出"由外部异步触发"这一形态。
4. **外设寄存器映射是类型**：MMIO 地址与位域用类型表达，编译期检查读写权限 —— 这一点对 AI 的价值极高（嵌入式 C 的指针/位运算错误是 AI 最高频、最致命的错误类别之一）。
5. **`host` 覆盖 FFI**：能链接任意 C 符号，嵌入式生态靠它，不靠我们重写驱动。

**战略含义**："同一门语言从 MCU 写到服务器"是一个足够大、且目前无人以"AI 优先"为口号占据的定位。它同时给了本项目一个比"又一个服务端语言"强得多的立项理由 —— 因为它要求的就是 §5.8 这个内存模型，而该模型恰好也是服务端资源正确性的最优解。**一个决定服务两头，这是整个设计里唯一的支点。**

## 11. 验证体系：证明"不需要海量数据"

**这一节决定项目成立与否。** 前面所有设计在拿到本节数据之前都只是主张。

### 11.1 语言规格书（人读 + 机读双份）

`SPEC.md` 必须 ≤ H1 预算；同时导出 `spec.json`（规则、错误码、性质模板），供代理与工具消费。**教学面预算本身是被测对象**（见 11.5）。

### 11.2 合成语料（不依赖自然语料）

新语言没有 GitHub 存量 —— 这是劣势也是机会：**语料可以完全合成、完全覆盖、且能定向制造难例。**

1. 由规范生成语法/语义测试程序（合法 + 每类非法各若干变体）；
2. 每条语言规则配 N 组"正例 / 常见误例 / 误例的正确改法"；
3. 从 §5.3/§5.7/§7.6 的声明生成"业务场景 → 代码"对（CRUD、鉴权、分页、幂等、重试、并发）。

**完成判据**：语料覆盖矩阵达到 **100% 规则覆盖**（每条规则至少有一个正例与一个误例）。这是可检查的，也是"不需要海量数据"的实际含义 —— 我们要的是**完备**，不是**海量**。

### 11.3 评测协议与指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 首次通过率 | 不带反馈一次写对的比例 | 语言本身的有效性 |
| 平均迭代轮次 | 到通过所需 check 次数 | 反馈循环效率 |
| **拦截率** | 失败中在编译期被拦下的比例 | 错误是否"便宜" |
| **误报率** | 被规则拦下但实际正确的代码比例 | **优先级高于拦截率**；误报会让代理学会绕过闸门 |
| 上下文成本 | 达到目标通过率所需的 token | 直接测 H1 |
| 语法层失败率 | 编译都没过的比例 | 应趋近 0，否则说明语法/先验有问题 |

任务分三档：单函数 / 单服务（多模块）/ 跨服务 + 外部故障注入。协议纪律：**不改断言、记录上下文注入档位、记录是否读过测试文件**（读过答案的结果只能当上界）。

### 11.4 归因设计：这是最重要的一项

"首次通过率高"有三种可能原因：语言好、反馈便宜、模型本来就行。必须用**消融实验**区分：

| 实验组 | 配置 | 检验的假设 |
| --- | --- | --- |
| **对照 0** | 现有语言（Go/TS）+ 同等时间投入 + 同等反馈工具 | 基线 |
| **对照 A** | droplet，**check 关闭**，一次写 | 语言自身（P-B） |
| **对照 B** | droplet，check 开启但只报错不给 hint | hint 的价值 |
| **对照 C** | droplet，check + hint + auto-fix | 完整机制（P-C） |
| **对照 D** | droplet，check + 无上下文注入 | 上下文依赖度（P-A） |

**判据**：C ≫ A 且 C > B ⇒ 证明"便宜可定位的反馈"是主因（P-C 成立）；D ≈ C ⇒ 证明语言足够小、不靠注入也能写对（P-A 强成立）；A 显著优于对照 0 ⇒ 语言结构有效（P-B 成立）。
**跨模型档位必测**（含小模型与非 agentic 模型）：闸门的价值在能力下段才显现，只在旗舰模型上测等于测不到。样本量 ≥ 30 任务、每任务 ≥ 3 次重复。

### 11.5 先于编译器做的"语义纸面验证"

**这是路线图第 1 阶段的核心手段，用来避免最贵的失败（写完编译器才发现假设不成立）。**

方法：用宿主语言（TS 或 Go）实现 droplet 的**类型/效果/资源检查器**，语法用 S-expression 或 C++ 风格外壳（语法不重要，语义才重要），实现 3–5 个真实服务端项目。然后测：

- 首次通过率、拦截率、误报率是否如预期；
- H1/H2/H3 预算是否守得住（实际写出规范需要多少 token？）；
- §5.8 的仿射 + 区域是否产生不可接受的误报（预判的"条件分支消费未定义"问题有多严重？）；
- 有多少 §3 的痛点被真正消灭，有多少被证明是语言管不了的。

**若第 1 阶段数据不达标，直接停止或改设计 —— 此时沉没成本是一份规范和一个检查器，而不是三年编译器。**

## 12. 分阶段路线图与 Go/No-Go 判据

| 阶段 | 交付物 | Go 判据 | No-Go 含义 |
| --- | --- | --- | --- |
| **S0 规范冻结** | `SPEC.md` v0 + 原语清单 + 错误码域 + 反模式清单 | 三条硬约束在纸面上满足（预算表算得过来）；每个特性都挂到 C1–C6 | 设计是特性堆叠，回去砍 |
| **S1 语义验证**（不写编译器） | 检查器原型（宿主语言实现）+ 3–5 个样例服务 + §11 全套实验数据 | 首次通过率显著高于同投入基线；误报率 < 5%；教学面实测 ≤ 预算 | **核心假设不成立，项目应重定位或终止** |
| **S2 引导实现** | 真语法 + C 后端 + `droplet check` + `droplet mem`/`droplet bench --gate` + 单一 std 子集 | 端到端跑通一个真实服务；跨后端符合性测试通过；**空服务 RSS ≤ 3 MB 实测达标（H4）** | 后端选型错误，或运行时机制过多，需回砍 |
| **S3 服务端最小可用** | DB/HTTP/边界/配置 四大件 + contract 导出 | 有 1–3 个**非作者**用户把服务跑上生产 | 生态成本 > 语言收益，考虑退化为某语言的 strict dialect |
| **S4 硬件后端** | MCU 目标 + MMIO 类型 + 内存上界报告（复用 §9.4 的 `droplet mem`） | 嵌入式场景验证"一门语言两头写"成立 | 两条赛道应拆成两个产品 |

**阶段纪律**：不允许跳过 S1 直接写编译器。语言项目的最大风险从来不是实现难度，而是"实现过程中投入越来越深，导致无人再检查前提"。

## 13. 已知风险与诚实的局限

1. **语义错误语言管不了。** 业务逻辑错、需求误解、算法设计错 —— 这是 AI 失效的头部来源，且不因换语言消失。本语言的合理目标是"消灭结构性错误"，不是消灭错误。若有人期待后者，本项目做不到。
2. **冷启动是最大现实风险。** 没有生态、没有驱动、没有用户。缓解靠 §7.4 契约机制 + C 后端的 FFI（`host` 块）+ 聚焦"服务端 + 嵌入式"这两处真正缺选项的场景。**不要试图第一天就做通用语言。**
3. **教学面预算会被持续挑战。** 用户会要求"就加一个便利函数"。H1 必须是 CI 检查项 + 章程条款，而不是我的自律。
4. **规则膨胀（错误码表变成产品）。** §2.3 准入判据 + §7.3"不许靠猜意图自动修"是防线；仍可能失败。
5. **新语言自身会变成新的 C6。** 唯一的防御是发布后不做语义不兼容变更（§4.1 章程条款）。
6. **误报比漏报更贵。** 代理遇到误报会寻找绕过手段（§3.6 的 `unwrap`/`allow` 教训）。因此：判定不确定的就不判（宁漏不误），并把"看不出的东西"写进文档明确交给验证层。
7. **仿射/区域对人的认知成本是真实的。** 我们主动承担它，理由是收益在 AI 侧且可延伸到硬件；但它会限制人的招聘与接受度 —— 这是本决策的已知代价，不是待解决问题。
8. **资源预算（§9）会与其余四条约束抢空间。** 静态链接推高二进制体积、有界栈限制递归、无 GC 让图结构变啰嗦、最小运行时与高吞吐互施压。裁决原则固定：**达到预算的方式只能是"减少运行时机制"，不能是"更激进的优化"或"放宽阈值"**。若 1 vCPU/512 MB 实测跑不动，说明机制清单没做完，而不是预算定错了。
9. **`check` 亚秒级在效果 + 资源流分析下技术上不轻松。** 这是性能工程约束，可能反向侵蚀设计（例如被迫做全局分析，而全局分析会带回级联错误）。**若冲突，优先级是"错误单点可解释"高于"检查快"**，与 §3.6 教训一致。
10. **本项目最终产物大概率不是"一门语言"，而是"语言 + 验证器 + 性质模板库"三件套。** 不可分割，也不应分割 —— 立项书不要只写语言。

## 14. 附录：原语清单与语法示意

### 14.1 原语盘点（对照 H3 ≤ 24）

| 类别 | 原语 | 计数 |
| --- | --- | --- |
| 数据 | record（结构）、sum（判别联合）、enum、bytes、str | 5 |
| 计算 | fn（闭包）、match、pipe | 3 |
| 状态 | region（区域）、cell（区域内可更新单值）、value（不可变绑定） | 3 |
| 效果 | effect（集合类型）、cap（能力）、handle（host 绑定） | 3 |
| 边界 | boundary（含版本与幂等标注） | 1 |
| 并发 | task（结构化）、chan（有界通道） | 2 |
| 服务面 | entry（入口，含鉴权/超时/重试预算） | 1 |
| 环境 | env（类型化配置，按环境实例化） | 1 |
| 类型 | opaque（不透明句柄）、id（类型化标识） | 2 |
| 失败 | err（联合的具名形态）+ ignore（显式留痕） | 2 |

**合计 24** —— 正好卡在 H3 上，说明**已无余量**。任何新增必须等量替换，这条要在 S0 阶段就固化。

### 14.2 关键字盘点（对照 H2 ≤ 14）

`fn` `let` `type` `match` `move` `end` `entry` `boundary` `env` `host` `task` `for` `if` `return` = **14**，同样无余量。
（区域、效果、能力用类型语法与属性表达，不占关键字；无 `class`/`interface`/`implements`/`try`/`catch`/`throw`/`async`/`await`/`defer`/`new`/`this`/`import`/`export`/`mut`/`unsafe`。）

### 14.3 语法示意（**形状占位，语义已定义**）

> 以下用 C 风格外壳仅为示意，用于 S1 阶段的语义验证；最终语法在 S2 定稿。语法不是本项目的主要假设，语义才是。

```droplet
// ── 1. 数据：不可变值 + 判别联合，match 必须穷尽 ──────────────
type Status { Active, Suspended { until: Time }, Deleted }

fn label(s: Status) -> str {
  match s {
    Active            => "ok",
    Suspended { at }  => "paused until " + show(at),
    // 少写 Deleted  => E1021 穷尽性错误（无 default 可逃）
  }
}

// ── 2. 效果与能力：能碰什么，写在参数上（无环境权限） ─────────
entry Users {
  // 效果集可见：只有 users 库的读权限 + 时钟
  fn summary(db: db[users:read], clock: Clock, id: Id<User>)
      -> Summary | NotFound | DbError
  {
    let u = get(db, id)!          // ! 向上传播；不写 ! 且不处理 => E0xxx 错误值被丢弃
    return Summary { name: u.name, age: years(clock, u.created) }
  }
}

// ── 3. 边界：跨进程数据是声明出来的一等事实 ──────────────────
boundary Payments @v1 {
  charge(id: Id<Order>, amount: Money) -> Receipt with idempotency
  // 无 with idempotency 的方法不可被重试效果调用 => E3xxx
}

// ── 4. 资源：仿射 + 区域。忘了提交/回滚、事务跨网络调用都编译失败
fn transfer(r: &region, a: Id<Account>, b: Id<Account>,
            x: Money, tx: db[accounts:write]) -> Ok | Insufficient
{
  let t = begin(tx)               // t 有类型 Tx，只在此作用域有效
  debit(t, a, x)!
  credit(t, b, x)!                // 这里 return Err 而未回滚 => E4xxx 二次使用/未消费
  commit(t)!                      // 不调用 commit => E4xxx（丢弃即释放，语义唯一）
}

// ── 5. 配置与环境：缺键在编译期失败，密钥不可读 ───────────────
env App {
  db_url: Secret
  stripe: Secret
  port: u16 = 8080
}

host main(cfg: App<prod>) {        // 环境必须能完整构造，否则 E6xxx
  serve(Users, on: cfg.port)       // cfg.db_url 无法被打印/写入日志（类型上不可构造）
}

// ── 6. 并发：结构化，无脱管任务 ──────────────────────────────
fn fan_out(cl: Clock, ids: [Id<User>]) -> [Summary]
{
  let out = spawn_in(cl) {         // 作用域结束前必须完成或被移交，否则 E5xxx
    for id in ids { task { fetch_one(id) } }
  }
  return collect(out)
}
```


## 附录 B：一句话总纲

> **不要设计一门更安全、更抽象、更优雅的语言；设计一门错误无法保持沉默、且验证以毫秒计、运行时轻到能塞进最小实例的语言。**
> AI 生成代码的错误率主要由"发现错误的时间与成本"决定，而不是由"语言有多聪明"决定 —— 本项目的全部设计，都是把这一句话翻译成语言构造。
>
> 而**省资源与防错是同一个动作**：隐形机制之所以隐形，是因为它在运行时替你做了一个源码里看不见的决定；它每做一次决定，就在内存里占一块地方。**AI 验证不了的东西，通常也正是最贵的东西。**

**下一步（S0 冻结前的四个必答问题）**

1. §5.8 的内存模型（仿射 + 区域）是全部设计唯一的支点，也是最可能翻车的一处 —— 需要单独出一份《资源语义专题》，把"条件分支上的消费未定义""区域借用与跨任务转移""`with` 自动作用域的覆盖边界"三种情形穷举清楚。
2. §9 的资源预算目前是**目标值不是实测值**。S1 阶段必须用真实原型回答：空服务 RSS 到底压到几 MB？有界栈的多深够用？无预分配调度器能不能守住空闲 0.5%？**这三条任何一条达不到，就要回到 §9.2 的清单继续删机制，而不是放宽阈值。**
3. §14.1/§14.2 的原语与关键字盘点已**卡在上限、零余量**。S0 阶段必须做一次"等量替换"演练：想加的每个特性，先指出它替换掉哪一个。
4. §11.4 的消融实验设计要在写任何代码之前定稿 —— 它决定这个项目能否区分"语言有效"和"运气好"。
