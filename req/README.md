# req/：文本需求 → 题面 → 验收

这一目录回答一个问题：**人不读实现、只验结果时，凭什么说“这一版是对的”？**

答案不是“相信 AI”，而是把“对的”拆成五条可失败的链子。缺任何一条，另外四条都能被绕开。

## 0. 先说清“翻译层”是什么，以及它不保证什么

原始需求是人写的散文。散文有两个毛病：一词多解，和**没有说错**。
把散文直接丢给 AI，错了也看不出来 —— 看不出来是翻译错了、需求本身错了，还是实现错了。

所以中间加一层，把散文变成**基于当前 C 实现可核对**的条款：

```
文本需求 → req/SRC.md（逐句编号）→ req/REQ.tsv（条款 + 源句 + 类型 + 证据）
                                      ↓
                        req/TRANS.tsv（每个条款选了哪种读法、排除了什么、反例、**这条反例归谁管**）
                        req/AMBIG.tsv（说不定的地方，未定 = 红）
                        req/GAP.tsv  （现有介质表达不了的承诺，状态 已闭/未闭/不闭）
                        req/BASELINE （基线 commit：先红后绿用它构建“旧实现 + 当前题面”）
```

这一层**不消除**风险，它把风险从“实现错了看不出来”挪到“翻译错了会红”。
翻译仍然可能错 —— 保证的是：**每个决定都留了名字，每个没决定的地方都会挡住提交。**

## 1. `SRC.md`：源句，逐句编号

一句一个 `S<n>`，只放原文的说法，不加解释。它是**唯一允许模糊的地方** ——
所有下游都要指回某个 `S<n>`。

## 2. `REQ.tsv`：条款 → 源句 → 类型 → 目标 → 断言/样例

七列，TAB 分隔，`#` 开头是注释，`-` 表示没有：

| 列 | 含义 | 失败条件 |
| --- | --- | --- |
| 编号 | `R1`、`R2`… | 重复或格式不对 |
| 条款 | 一句没有歧义的话 | 为空 |
| 源句 | `SRC.md` 里的 `S<n>`，逗号分隔 | 引用不存在的源句；源句没人认领 = 孤儿 |
| 类型 | `回归` / `新增` / `缺口` | 别的值 |
| 目标 | `DP_GOALS` 里的 id，逗号分隔 | 引用不存在的目标 |
| 断言 | `accept-table.sh` 里的编号，逗号分隔 | 引用了不存在的断言 |
| 样例 | `DP_EXAMPLES` 里的编号，逗号分隔 | 引用了不存在的样例 |

三条类型口径：

- **回归** = 当前实现已经做到了，验的是别改坏；
- **新增** = 当前实现还没做到，这次要它做到（必须能在基线上**先红**）；
- **缺口** = 现在的介质表达不了这条承诺（见 `GAP.tsv`），**不许写证据**，写了就是假装有证明。

`python3 code/sup/req-check.py <二进制>` 逐条核对，并且要求：

- 每条条款至少有一条断言或样例撑着（只有文字 = 未证）；
- 每条断言、每条样例、每条目标、**每个源句**都至少被一条条款认领（孤儿 = 红）；
- 条款写的断言集合必须等于它声明的目标所证明的集合（一边改了另一边没改 = 漂移）；
- 每个条款在 `TRANS.tsv` 里**恰好一行**，五个字段（原文/译法/排除/反例/证据）都不为空；
- `AMBIG.tsv` 里有“未定”= 红；`GAP.tsv` 的状态只允许 已闭 / 未闭 / 不闭，`未闭` = 红；
- `缺口` 条款必须有对应 GAP 行；`回归`/`新增` 条款也可以有 GAP 行（那是在承认边界），
  但**每行 GAP 的编号必须被它挂的那条反例文本点名** —— 否则缺口是别人笔记里的缺口，不是这条需求的。

口径：断言来自验收脚本本体，目标/样例来自 `blobd --contract` 的编译产物，不读实现源码。
所以改名、挪函数、换写法都不会让登记表“假绿”。

## 3. `TRANS.tsv`：翻译台账（这一层的正身）

六列：`R`、`原文`、`译法`、`排除`、`反例`、**`证据`**。

- **译法**：这次选择把条款写成什么样的检查（越具体越好，比如“body 精确等于 …”）；
- **排除**：明确说了不约束什么（空白、转义、没测的变体 —— 沉默不算排除）；
- **反例**：什么样的错实现能骗过这条检查。写不出反例，说明这条检查是同义反复；
- **证据**（v0.37 新增）：这条反例**现在归谁管**。三种编号可以混写：
  `S<n>` = `mutation-score.py` 的实现变异（实测必须弄红本条款声明的某条断言）；
  `E<n>` = `DP_EXAMPLES` 的样例（实测必须“翻转期望就挂”，且本条款必须声明它）；
  `-` = 现在没人管 —— 反例写“无（译法与原文同宽）”时必须是 `-`；写了真反例却只填 `-`，
  就必须有一条 `GAP` 行，且那个 `G<n>` 要出现在反例文本里。

`反例` 这一列是防“循环翻译”的：如果译法只是把现状抄一遍，反例那一栏必然空着。
`证据` 这一列是防“反例写成散文”的：v0.36 之前它能写一句“某某实现能骗过去”就完事，
没人问过那句到底是谁在管。现在它必须是一个能被实测查到的编号 —— `mutation-score.py --phase all`
的“台账对账”那一段就是查这个的，说管不住 = 红。

## 4. 先红后绿：`req/BASELINE` + 自动基线（v0.37 起不用人跑）

```sh
python3 code/sup/req-check.py <新二进制>            # 有“新增”条款时自动跑基线核对
python3 code/sup/req-check.py <新二进制> --no-baseline   # 快速回路：显式跳过（结论里会写明这一层没走完）
python3 code/sup/req-check.py <新二进制> --baseline <二进制|commit>   # 也可以手给
```

`req/BASELINE` 里是一行 commit（由 `freeze.sh --update` 在换题时钉成**此刻的 HEAD**；
文件已存在就不覆盖，要换基线是“删掉它再 `--update`”这样一个显式动作）。有 `新增` 条款时
`req-check` 调 `baseline-sup.sh`：`git archive <基线>` 导出旧实现，**只覆盖题面**（验收表、声明头、
`req/` 五份译稿），绝不覆盖 `blobd.c` / `dp_decide.c` / `rt_*.c` —— 否则就是拿新实现验新实现。
构建结果按 `sha + 题面 cksum` 缓存，题面没动就复用。然后要求：

- 每条 `回归` 条款的证据在基线上**全绿**（回归条款在旧实现上就红 = 登记抄错了或题变了）；
- 每条 `新增` 条款至少有一条断言在基线上**是红的**（新增条款在旧实现上就绿 = 翻译抄了现状，
  或者写成了一条永远为真的检查）。

两个只有跑了才会撞上的坑：

1. **换题时上一轮的 `新增` 必须改成 `回归`**。它已经实现了，还挂着 `新增` 的话，基线上它全绿 ——
   门会红着说“新增条款在基线上全是绿的”。这不是罚你，是提醒类型这一列是**相对基线**的说法。
2. **本轮的基线是手钉的**。`a4996db` 把“换题”和“实现”写进了同一个 commit，那一刻的 HEAD 已经是
   做完的版本，`--update` 会自证。所以 `req/BASELINE` 里写的是上一轮的 HEAD（`89a310f`），
   这件事连同理由写在文件头的注释里。
3. CI 的默认浅 clone 导不出旧树（假红），`.github/workflows/ci.yml` 的 checkout 因此带 `fetch-depth: 0`；
   破坏测试 #18 专门验“把基线钉成当前 HEAD 必须被认出是自证”。

这一条是翻译层里唯一直接对**实现**下判断的检查。过去它最贵的地方是“要留一个旧二进制”，现在
贵的是首次构建那 ~10 秒，之后按题面哈希复用。

## 5. `FROZEN`：题面不能动

`code/sup/freeze.sh --update` 把十一份题面文件（验收表、`dp_decide.h`、`dp_env.h`、
`dp_sup.h`、`dp_conf.h`、`rt.h`，加上 `req/` 五份译稿）与 `blobd --contract` 的原始输出
各钉一个 sha256。

- `check.sh` 每次都核对；
- `submit-sup.sh` 在构建之后、跑样例之前核对；不一致就拒绝，理由写“题被改过”；
- 只有人类显式 `--update` 才能换题。换题是一个动作，不是一次顺手的编辑。

**为什么契约哈希不会误伤实现**：`--contract` 只由四张声明表生成，函数体怎么改都不变。
所以“只交 `dp_decide.c` 的实现”不会撞墙；改表（路由、目标、样例、边界）才需要重新冻结。

**为什么译稿也要钉**：`REQ.tsv` 与 `TRANS.tsv` 就是题。把 `新增` 改成 `回归`、把反例那一栏删空，
都能让“全绿”变得没有意义。

## 6. `mutation-score.py`：每条断言与每条样例都得会红

三个方向加一相对账：

- **L（表自检）**：把第 N 条断言的期望改成 `__IMPOSSIBLE__`，必须恰好红 #N、其余全绿。
  不红 = 这条断言没被执行；红了别的 = 表之间有隐藏耦合。
- **E（样例自检，v0.37）**：把 `DP_EXAMPLES` 第 N 条的期望取反，必须恰好挂 #N。
  样例只在决定层跑、没有服务端响应可看，最容易退化成摆设 —— 没有这一相，`TRANS` 里写 `E<n>` 就没法验。
- **S（实现灵敏度）**：若干条源码变异（每条只改一处、锚点唯一、在临时树里构建），
  事先声明应该红哪几条断言；实际红集合必须包含声明集合，否则归因不符。
  覆盖分 = 至少被一条变异弄红的断言数 / 断言总数（从验收表数出来，不写死），低于 floor 直接红。
  **floor 钉成断言总数（现 30）**：加一条断言就得同时交出“能把它弄红的那一改”。
- **台账对账**（`--phase all`）：`TRANS` 证据列认领的 `S<n>` 必须真的弄红本条款声明的断言、
  `E<n>` 必须在 E 相活着且被本条款声明。说管不住 = 红。

它证明的是“断言能分辨实现好坏”，**不证明**“断言覆盖了需求的全部”。后者由第 2、3 条负责。

## 7. `report.sh`：给人看的一页

按条款组织，不按断言编号组织：每行列出**源句、类型、需求、断言/样例编号**和这一版的红绿；
页脚显示译稿对账份数、歧义与缺口状态、未证目标、题面冻结与登记链状态。
没跑 `--accept` 就写“未跑”，不拿上一次的绿冒充这一次。

## 8. 人的操作顺序

```sh
# 1) 把文本需求逐句写进 req/SRC.md，译成 REQ/TRANS，说不定的进 AMBIG，表达不了的进 GAP
# 2) 人类确认题面，冻结（换题就重跑）
sh code/sup/freeze.sh --update .build/sup/blobd

# 3) 登记 + 基线核对：证明回归没坏、新增确实是新增（基线自动从 req/BASELINE 构建）
python3 code/sup/req-check.py .build/new/blobd --port 18600

# 4) 把 req/ 与题面包交给 AI；AI 只改实现
# 5) 提交
sh code/sup/submit-sup.sh 候选.c 18882

# 6) 人看一页
sh code/sup/report.sh .build/check/blobd --accept 18881
```

## 9. 一轮完整验证（S14 → R17，2026-11-02）

文本需求只有一句：**“清单响应必须是一个 JSON 对象，顶层键 `keys`，值是按字典序排列的字符串数组。”**

| 步骤 | 结果 |
| --- | --- |
| 登记 | `S14` → `R17`，类型 `新增`，目标 `list_envelope`，断言 `#27`（精确等于 `{"keys":["demo","second","third"]}`） |
| 台账 | `TRANS` 排除空白/转义；反例写“只查前缀会漏掉值被写成数字数组” → 所以用精确 body |
| 基线（旧实现） | 回归 16 条全绿；`#27` 在旧实现上是红的（旧实现回裸数组）→ 先红 |
| 冻结 | `freeze.sh --check` 先红（题面确实变了），人类 `--update` 后 12 项一致 |
| 实现 | `dp_blob_list` 输出 `{"keys":[...]}`，空目录回 `{"keys":[]}` |
| 验收 | 27/27 绿，`#27` 观测到的是 `{keys:[demo,second,third]}` |
| 变异 | `S21`（退回裸数组）与 `S22`（排完再倒序）都必须恰好红 `#27` |

这一轮同时验到了翻译层的三个陷阱：
`dp_blob_list` **本来就已经排序** —— 如果照“按字典序”这句直接登记，`#27` 在基线上就是绿的，
`--baseline` 会把这条“抄现状”的翻译判红；真正没做到的是外壳。
排除列也不是装饰：key 字符集受限，所以不约束 JSON 空白是**写明**的排除，不是漏掉。

### 9.1 又一轮：一次没测出正差异的 A/B，产出两条登记（S15/S16 → R18/R19，2026-11-02，v0.37）

拿“清单改成 JSON 对象”这件事做了两轮 A/B：一臂只给散文，一臂给 `req/` 译稿包，12 份实现，
**两臂全对、0 次分岔** —— 译稿层“让实现更正确”这一条没测出来（EXPERIMENT §3）。
有用的是它逼出来的两处漏账：

| 步骤 | 结果 |
| --- | --- |
| 发现 | 只有读译稿的臂提出“Content-Type 归谁保证”（0/3 vs 2/3）；“目录读不到算不算空的”两臂都提（3/3 vs 3/3） |
| 登记 | `S15`/`S16` 两句挂「【补，散文未写】」→ `R18`/`R19`，类型都是 `回归`（实现早就在做） |
| 判据 | 断言 `#28`（带表示的成功响应声明 `application/json`）、`#30`（数据目录指向普通文件 -> 拒绝启动 + 留诊断） |
| 目标 | `content_type_json` / `boot_requires_usable_root` 进 `DP_GOALS`，各自指名一条断言 |
| 台账 | `R18` 证据 `S24`、`R19` 证据 `S25` —— 两条都是**新写的实现变异**，实测分别弄红 `#28`/`#30` |
| 缺口 | `G8`（空清单没判据）用 `#29` **已闭**；`G9`（目录不可读没判据）用 `#30` **已闭**；其余 7 条写的是 `不闭` |
| 一次台账错 | `AMBIG A4` 初稿写“不可读 -> 500”。跑探针才发现实现是 **fail fast**：`stat` 失败或非目录就退出码 1。台账按实现改 |

`#30` 是这张表里唯一一条不问 HTTP 的断言。它能存在，是因为 A/B 里那份“没把握清单”问了
一句“目录读不到怎么办” —— 而 29 条断言没有一条问过。


## 10. 边界（别把它说大）

- 这五道门保证的是**“与登记的译稿一致，且错了会红”**，不保证译稿本身翻对了；
- 翻译错误仍然可能发生 —— 门只让它在 `TRANS`/`AMBIG`/`GAP`/基线四处**暴露出来**，而不是消失。
  本轮就有一处：`A4` 的读法与实现不一致，是靠跑探针发现的，不是靠对账发现的 —— 台账对账验的是
  “编号存在且实测能红”，它验不出“这句话本身写错了”；
- 运行时的行为只有在 wire 断言里被写到的部分才被验（长稳、真实磁盘满、并发压力不在里面）；
- 变异覆盖分衡量的是断言灵敏度，不是代码质量；
- 所以“实现 100% 正确”仍然不可保证。可以保证的是：**已知的错法会被具体工具指名抓住**，
  **题被改动时不会静默通过**，以及**每一次翻译都留下了可追责的痕迹**。
