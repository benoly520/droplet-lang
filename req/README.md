# req/：需求登记与题面冻结

这一目录回答一个问题：**人不读实现、只验结果时，凭什么说“这一版是对的”？**

答案不是“相信 AI”，而是把“对的”拆成四条可失败的链子。缺任何一条，另外三条都能被绕开。

## 1. `REQ.tsv`：条款 → 目标 → 断言/样例

五列，TAB 分隔，`#` 开头是注释，`-` 表示没有：

| 列 | 含义 | 失败条件 |
| --- | --- | --- |
| 编号 | `R1`、`R2`… | 重复或格式不对 |
| 条款 | 一句人话需求 | 为空 |
| 目标 | `DP_GOALS` 里的 id，逗号分隔 | 引用了不存在的目标 |
| 断言 | `accept-table.sh` 里的编号，逗号分隔 | 引用了不存在的断言 |
| 样例 | `DP_EXAMPLES` 里的编号，逗号分隔 | 引用了不存在的样例 |

`python3 code/sup/req-check.py <二进制>` 逐条核对，并且额外要求：

- 每条条款至少有一条断言或样例撑着（只有文字 = 未证）；
- 每条断言、每条样例、每条目标都至少被一条条款认领（孤儿 = 红）；
- 条款写的断言集合必须等于它声明的目标所证明的集合（一边改了另一边没改 = 漂移）。

口径：断言来自验收脚本本体，目标/样例来自 `blobd --contract` 的编译产物，不读实现源码。
所以改名、挪函数、换写法都不会让登记表“假绿”。

## 2. `FROZEN`：题面不能动

`code/sup/freeze.sh --update` 把六份题面文件（验收表、`dp_decide.h`、`dp_env.h`、
`dp_sup.h`、`dp_conf.h`、`rt.h`）与 `blobd --contract` 的原始输出各钉一个 sha256。

- `check.sh` 每次都核对；
- `submit-sup.sh` 在构建之后、跑样例之前核对；不一致就拒绝，理由写“题被改过”；
- 只有人类显式 `--update` 才能换题。换题是一个动作，不是一次顺手的编辑。

**为什么契约哈希不会误伤实现**：`--contract` 只由四张声明表生成，函数体怎么改都不变。
所以“只交 `dp_decide.c` 的实现”不会撞墙；改表（路由、目标、样例、边界）才需要重新冻结。

## 3. `mutation-score.py`：每条断言都得会红

两个方向：

- **L（表自检）**：把第 N 条断言的期望改成 `__IMPOSSIBLE__`，必须恰好红 #N、其余 25 条绿。
  不红 = 这条断言没被执行；红了别的 = 表之间有隐藏耦合。
- **S（实现灵敏度）**：20 条源码变异（每条只改一处、锚点唯一、在临时树里构建），
  事先声明应该红哪几条断言；实际红集合必须包含声明集合，否则归因不符。
  覆盖分 = 至少被一条变异弄红的断言数 / 26，低于 floor 直接红。

它证明的是“断言能分辨实现好坏”，**不证明**“断言覆盖了需求的全部”。后者由第 1 条负责。

## 4. `report.sh`：给人看的一页

按条款组织，不按断言编号组织：`R1…R16` 各自列出断言/样例编号和这一版的红绿；
同时显示未证目标、题面冻结状态、登记链状态。没跑 `--accept` 就写“未跑”，
不拿上一次的绿冒充这一次。

## 5. 人的操作顺序

```sh
# 1) 人类确认需求与题面，冻结
sh code/sup/freeze.sh --update .build/sup/blobd

# 2) 把 req/ 与题面包交给 AI；AI 只改 dp_decide.c（或按题面实现）
# 3) 提交
sh code/sup/submit-sup.sh 候选.c 18882

# 4) 人看一页
sh code/sup/report.sh .build/check/blobd --accept 18881
```

## 6. 边界（别把它说大）

- 这四道门保证的是**“与登记的需求一致，且错了会红”**，不保证需求本身写对了；
- 运行时的行为只有在 wire 断言里被写到的部分才被验（例如长稳、真实磁盘满、并发压力不在里面）；
- 变异覆盖分衡量的是断言灵敏度，不是代码质量；
- 所以“实现 100% 正确”仍然不可保证。可以保证的是：**已知的错法会被具体工具指名抓住**，
  以及**题被改动时不会静默通过**。
