# 登记介质：五份文件（TAB 分隔）

要登记的工程清单见 inventory.json，需求见 TASK.md。
交付：把登记写进你被指定的文件，格式按下面的列口径。

## 1. `SRC.md`：源句，逐句编号

一句一个 `S<n>`，只放原文的说法，不加解释。它是**唯一允许模糊的地方** ——
所有下游都要指回某个 `S<n>`。

## 2. `REQ.tsv`：条款 → 源句 → 类型 → 目标 → 断言/样例

七列，TAB 分隔，`#` 开头是注释，`-` 表示没有：

| 列 | 含义 | 失败条件 |
| --- | --- | --- |
| 编号 | `R1`、`R2`… | 重复或格式不对 |
| 条款 | 一句没有歧义的话 | 为空 |
| 源句 | `SRC.md` 里的 `S<n>`，逗号分隔 | 引用不存在的源句；源句没人认领 = 孤儿 |
| 类型 | `回归` / `新增` / `缺口` | 别的值 |
| 目标 | `DP_GOALS` 里的 id，逗号分隔 | 引用不存在的目标 |
| 断言 | `accept-table.sh` 里的编号，逗号分隔 | 引用了不存在的断言 |
| 样例 | `DP_EXAMPLES` 里的编号，逗号分隔 | 引用了不存在的样例 |

三条类型口径：

- **回归** = 当前实现已经做到了，验的是别改坏；
- **新增** = 当前实现还没做到，这次要它做到（必须能在基线上**先红**）；
- **缺口** = 现在的介质表达不了这条承诺（见 `GAP.tsv`），**不许写证据**，写了就是假装有证明。

`python3 code/sup/req-check.py <二进制>` 逐条核对，并且要求：

- 每条条款至少有一条断言或样例撑着（只有文字 = 未证）；
- 每条断言、每条样例、每条目标、**每个源句**都至少被一条条款认领（孤儿 = 红）；
- 条款写的断言集合必须等于它声明的目标所证明的集合（一边改了另一边没改 = 漂移）；
- 每个条款在 `TRANS.tsv` 里**恰好一行**，五个字段（原文/译法/排除/反例/证据）都不为空；
- `AMBIG.tsv` 里有“未定”= 红；`GAP.tsv` 的状态只允许 已闭 / 未闭 / 不闭，`未闭` = 红；
- `缺口` 条款必须有对应 GAP 行；`回归`/`新增` 条款也可以有 GAP 行（那是在承认边界），
  但**每行 GAP 的编号必须被它挂的那条反例文本点名** —— 否则缺口是别人笔记里的缺口，不是这条需求的。

口径：断言来自验收脚本本体，目标/样例来自 `blobd --contract` 的编译产物，不读实现源码。
所以改名、挪函数、换写法都不会让登记表“假绿”。

## 3. `TRANS.tsv`：翻译台账（这一层的正身）

六列：`R`、`原文`、`译法`、`排除`、`反例`、**`证据`**。

- **译法**：这次选择把条款写成什么样的检查（越具体越好，比如“body 精确等于 …”）；
- **排除**：明确说了不约束什么（空白、转义、没测的变体 —— 沉默不算排除）；
- **反例**：什么样的错实现能骗过这条检查。写不出反例，说明这条检查是同义反复；
- **证据**（v0.37 新增）：这条反例**现在归谁管**。三种编号可以混写：
  `S<n>` = `mutation-score.py` 的实现变异（实测必须弄红本条款声明的某条断言）；
  `E<n>` = `DP_EXAMPLES` 的样例（实测必须“翻转期望就挂”，且本条款必须声明它）；
  `-` = 现在没人管 —— 反例写“无（译法与原文同宽）”时必须是 `-`；写了真反例却只填 `-`，
  就必须有一条 `GAP` 行，且那个 `G<n>` 要出现在反例文本里。

`反例` 这一列是防“循环翻译”的：如果译法只是把现状抄一遍，反例那一栏必然空着。
`证据` 这一列是防“反例写成散文”的：v0.36 之前它能写一句“某某实现能骗过去”就完事，
没人问过那句到底是谁在管。现在它必须是一个能被实测查到的编号 —— `mutation-score.py --phase all`
的“台账对账”那一段就是查这个的，说管不住 = 红。



### req/REQ.tsv（列与口径）

```
# Droplet 需求登记：源句 -> 条款 -> 目标 -> 断言/样例
#
# 列：编号 <TAB> 条款 <TAB> 源句 <TAB> 类型 <TAB> 目标 <TAB> 断言 <TAB> 样例
#   源句：req/SRC.md 里的 S 编号，逗号分隔；每条条款至少引一句，每句至少被一条条款认领。
#   类型：回归 = 现状已满足、留作护栏；新增 = 实现前必须是红的（先红后绿）；缺口 = 当前机制表达不了。
#   “-” 表示这一栏没有。除“缺口”外，每条条款都必须至少有一条断言或样例撑着。
# 改这一张表等于改“需求是什么”，必须和 req/FROZEN 一起更新（见 req/README.md）。
```

### req/TRANS.tsv（列与口径）

```
# 语义差异单：每条条款是怎么从源句译过来的，以及那条反例现在谁在管
#
# 列：条款 <TAB> 源句 <TAB> 译法（选了哪种读法） <TAB> 排除了什么 <TAB> 反例（满足译法却违反原意的实现） <TAB> 证据
# “反例”写“无（译法与原文同宽）”才算过关；写得出反例，说明译法比原文窄，必须补断言或进 AMBIG。
#
# “证据”这一列把反例交给机器对账（v0.37），三种编号：
#   S<n> = code/sup/mutation-score.py 里的实现变异，实测必须弄红本条款声明的某条断言；
#   E<n> = DP_EXAMPLES 里的样例，实测必须“翻转期望就挂”（X 相）；本条款必须声明这个样例；
#   “-”  = 这条反例眼下没人管 —— 那就必须在 req/GAP.tsv 里有一行，并把编号写进反例文本。
# 规则由 req-check（静态）+ mutation-score（实测）两头查：
#   反例非“无…” -> 证据列非空 或 GAP 有行；每个 S/E 编号必须存在且真的打得中本条款；
#   每个变异/样例必须被某条条款认领（孤儿 = 红）；每个 GAP 编号必须出现在其条款的反例里。
# 这一张表仍然是给人签的，但“签了却没账”现在会红。
```

### req/AMBIG.tsv（列与口径）

```
# 歧义台账：原文有两种以上读法的地方，选了一种就必须写出来
#
# 列：编号 <TAB> 源句 <TAB> 读法A <TAB> 读法B <TAB> 选择 <TAB> 判定证据 <TAB> 状态
# 状态只允许“已定”或“未定”；未定 = req-check 红，不能提交。
# 判据来自哪一栏也写在“判定证据”里：写成断言/样例编号，不写“大家都这么用”。
# 读法不是越全越好：写得出“哪种实现满足A却违反B”，这条歧义才是真的。
```

### req/GAP.tsv（列与口径）

```
# 机制缺口：这条需求当前验不到哪一步，以及谁在看着它
#
# 列：编号 <TAB> 条款 <TAB> 缺什么机制 / 缺哪条判据 <TAB> 状态
# 状态三种，含义不同，别混：
#   未闭 = 这一条挡路：req-check 直接红，不许带着它继续实现；
#   不闭 = 承认这是当前口径下的边界，不挡路，但它必须出现在条款的反例文本里（编号被引用），
#          于是它在验收页上一眼能看见 —— “不闭”不是“删掉”，是“挂着让人看”；
#   已闭 = 曾经没判据、现在有了：闭合它的断言/样例编号要写进文本，反例列也要引用这个编号。
#
# 为什么要有这张表：v0.36 之前它是空的，原因是没人去看 TRANS 的“反例”列里那些
# “未断言，已知边界”——它们写在私人笔记里，等于没写。v0.37 起 req-check 会拿
# TRANS 的证据列对账：写了反例、又没人管、又没登记缺口 -> 红。
```
